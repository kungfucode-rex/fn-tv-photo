# 自定义背景音乐 —— 设计

> **状态：已实现（1.5.5，2026-10-12）并在 Android TV 模拟器上验收过。** 本文是曲库、两条入口
> （扫码上传 / 本机与 U 盘目录）和播放规则的**唯一真相源**：实现与它不一致时，先改文档或改实现，
> 不要两处各说各的。1.5.1–1.5.3 的三轮改动（页面重做、内置只留一首、去掉扫描）都记在
> [verification.md](verification.md) 第 25 条。
> 目标读者：未来的我自己。风格对齐 [tuping-design.md](tuping-design.md)。

## 0. 一句话

幻灯片的内置四首之外，用户可以把 mp3 放进电视：**手机扫码上传**，或者**从电视本机 / U 盘
的音乐里选**。搬进来的曲子进电视本地的一个曲库目录，播放永远读本地文件。

## 1. 已定的决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | **播放只读本地**（`assets` 或曲库目录），网络只负责"把歌搬进来" | `SlideshowMusic.kt:12-19` 已经把理由写死了：配乐必须和幻灯片同时开始，一首还要先认证、先缓冲的曲子会让每次开场先来一段静音。本地化之后 NAS 休眠、断网、外网慢都不影响放映，播放器也几乎不用改 |
| D2 | **不做飞牛音乐库导入**（原方案的 WebDAV 入口，2026-10-12 决定砍掉） | 飞牛音乐没有公开 API（官方开放平台只有文件授权类 scope，见 [fnos-access-research.md:392-402](fnos-access-research.md#L392-L402)），只能走 WebDAV：多一套协议、凭据、目录浏览器、下载与进度，是这一版里最贵的部分，而用户真正要的两个场景（扫码、拷进目录）已经覆盖。留好接口，将来要加只是一个"导入器"（§9） |
| D3 | 扫码上传**由电视自己承载**：内嵌一个 HTTP 服务 + 内嵌 H5 页，不依赖图评服务端 | 图评是可选的第三方组件（README 的部署章节自己就这么说）。"自定义音乐"不该因为没装图评就不能用，也不该为了这个功能要求用户去跑一个 Docker 容器 |
| D4 | 加 `com.google.zxing:core`，**只用来编码** | 现在二维码是服务端渲染的 —— `ReviewClient.kt:156-172` 只是拉一张 PNG —— 电视自己没有编码器。zxing core 是纯 jar、不联网、不要相机权限，是这里最小的一步；手写 QR 编码器不值得，让用户手输 IP 又不友好 |
| D5 | 曲库目录取 `getExternalFilesDir()/music`，**取不到才回退** `filesDir/music` | 电视盒子的内部存储常常只剩一两 GB，外部私有目录一般更大；两者都不需要任何存储权限。**不放进 `cache/image_cache`**：那是图片缓存，有 5 GB LRU 淘汰，会**悄悄删掉用户的音乐** |
| D6 | 上传服务**只写曲库目录**，不要全盘访问权限 | 不引入 `MANAGE_EXTERNAL_STORAGE`：很多电视根本没有授予它的入口，而这个功能不需要它 |
| D7 | 曲目的 id 就是它的路径；**选择按 id 存**，文件不在就丢弃 | 沿用既有语义（`SettingsStore.kt:92`、`normalizeMusicSelection`）：一份存坏的偏好自己会好，而不是留下一个播不出来的条目 |
| D9 | **内置只留一首**（1.5.2 起） | 手机十秒就能把歌传上来之后，随每个 APK 分发四首商业录音就是没人会选的 10.7 MB；留一首只为一件事 —— 全新安装也有东西可放。包从 25.9 MB 降到 15.8 MB |
| D10 | **列表与播放顺序是同一个**，不分内置／上传（1.5.2 起） | 序号只有一个连续序列，四首内置也排在同一个列表里。分组头、以及"内置不能删不能排"的规则都随之消失 —— 一张有 4 行排不动的列表，用户其实排不了 |
| D11 | 删内置 = **从列表里去掉**，并且可恢复（1.5.2 起） | 它的文件在 APK 里，删不掉。所以记一条"已移除"，并给一行 `恢复内置曲目`：一个既不能撤销、又释放不了任何空间的删除，是两头都占的坏结果 |
| D12 | **删掉扫描本机 / U 盘**（1.5.3 起） | 遥控器按着去 U 盘里挑歌没人做，而手机上传就在同一页；代价却是两个存储权限、一次授权框、一类"文件被拔走"的行，以及穿过删除路径的"我们的拷贝 vs 你的文件"。删掉后 manifest 不再申请任何存储权限（§5） |
| D8 | 新增的曲目**不自动勾选**（除非当前一首都没勾） | 勾选/取消会让播放列表重载（音乐从头开始）。上传一首歌就把正在听的曲子打断，是"添加"这个动作不该有的副作用 |

### 1.1 这一版明确不做的事

飞牛音乐库 / WebDAV / SMB / DLNA 导入；在线串流播放（理由见 D1）；系统文件选择器（SAF，见 §9）；
`MANAGE_EXTERNAL_STORAGE`；逆向音乐 App 的私有接口；歌词、封面、均衡器、音量控制。

## 2. 曲目模型与存储

### 2.1 三种来源

| 来源 | 文件在哪 | 什么时候出现 | 断链时 |
| --- | --- | --- | --- |
| **内置** | APK `assets/music/`（四首） | 永远 | 不会断（跟着 APK） |
| **上传** | 曲库目录（复制进来） | 扫码上传成功，或用数据线拷进去 | 不可能：文件在曲库目录里 |


两种来源其实是同一件事：**都是这个目录里的一个文件**。哪种方式把它放进来的，列表不关心；
它来自哪里只写在行尾的标签上（内置／手机上传）。

### 2.2 存储格式

选择（ticked）沿用现有的一行一条、纯文本、能在 bug 报告里直接读的格式（`SlideshowMusic.kt:60-67`）：

```
music/yuehui-kikujiro-piano.mp3          ← 内置：assets 路径，与旧版本存下来的值完全一致
file:/…/files/music/月亮照山川.mp3         ← 自定义：`file:` + 绝对路径
```

- **旧偏好无需迁移**：内置条目的写法没有变，`decodeMusicSelection` 读到的老值照旧命中。
- 引用列表（扫描发现、被导入过的本机文件）另存一条偏好，与"勾选"分开：**勾选**决定播什么，
  **引用列表**决定列表里显示什么。混在一起的话，取消勾选会让文件从列表里消失，用户就再也勾不回来了。
- 曲目顺序 = 内置（目录顺序，`SlideshowMusic.kt:27`）在前，自定义**按名称排序**在后。既有约定是
  "按目录顺序而不是勾选顺序"（`SlideshowMusic.kt:46-54`）：名称序是用户能自己看懂、能自己预测的那一种，
  加入时间序不能。

### 2.3 标题与元数据

标题优先取 ID3（系统自带的 `MediaMetadataRetriever`，不加依赖），取不到就用文件名（去扩展名）。
`retriever` 在个别盒子上对畸形文件会抛异常或返回 null，所以它**必须有兜底**，并且失败不能让扫描整体失败。
时长同时拿到，用来做 §5 的过滤和列表右侧的显示。不读封面（这一版没有封面位）。

## 3. 界面

### 3.1 上传页（`Screen.Music`）

一个屏幕装下整件事：左边是标题、二维码和说明，右边是列表。从**查看器曲目列表最后一行**
（`＋ 上传 / 管理背景音乐…`）和**设置 → 幻灯片设置 → 上传背景音乐**两处进入，Back 回到各自来源 ——
导航栈记得住，页面自己什么都不用记（设置页那一侧另见 §3.4）。

左边：标题「上传背景音乐」；二维码（白卡片就是静区）；可读地址；三行步骤；`已收到 N 首 · X MB`
与最近两条上传结果；`已用 x / y`；一句"上传期间请留在这一页；扫码打不开先查同一 Wi-Fi 与 AP 隔离"。

右边是**一个带序号的滚动列表**，序号从 1 连续编到 N —— 这就是播放顺序：

| 行 | 行为 |
| --- | --- |
| 曲目 | OK 选中／取消；**长按**进入 §3.2 的两个小按钮 |
| `恢复内置曲目 (N)` | 只在删过内置曲目时出现，把它放回列表末尾 |
| `清空我的音乐 (N)` | 只在有上传时出现，删掉那些拷贝 |
| `曲库目录` | 不可获焦的信息行，写着完整路径 —— 用数据线拷进去的文件和上传的一样会被列出来 |

**没有分组头。** 1.5.2 起不再区分「内置」与「我的音乐」：列表就是播放列表，序号是一个连续序列，
分组头只会描述一个顺序已经不再做的区分。一行来自哪里写在行尾的小标签上（内置／手机上传）。

### 3.2 长按后的两个小按钮

长按某一行（约 400 ms）在行尾浮出 `排序` 与 `删除`，行本身被点亮。**两个按钮出来后没有任何一个是选中的** —— 长按之后必须先用左右键选中一个，OK 才会执行；同一次长按剩下的 auto-repeat 与那一下松手也一律忽略。理由是一次真机反馈：按钮出来时若已经预选了 排序，`松手` 那一下就会执行它，紧接着的一个 repeat 事件又被读成"往下移"，于是一次长按自己把列表改了。

- ← / → 在两者之间切换（循环），OK 执行高亮的那一个，Back 收起
- **排序**：这一行上下出现 ▲▼，↑ / ↓ 把它往上／往下挪一位；顺序**每挪一次就存一次**，所以 Back
  就是"确认" —— 它只需要退出这个模式。挪到顶／底再按不再移动（不环绕：一张列表的两端是"上移"
  应该停止生效的地方）`movedWithinOrder` 有单测
- **删除**：上传的曲子连文件一起删；内置那首**删不掉文件**（它在 APK 里），所以删除只表示
  "不再出现在我的列表里"，并且可以恢复 —— 这是唯一一种可撤销的删除，也是 `恢复内置曲目` 存在的理由
- 两个模式里 ↑ / ↓ 都不会把光标移出这一行；Back 一律退出到普通模式

模式机是纯逻辑（[`ui/music/UploadPageModel.kt`](../app/src/main/java/com/tvphoto/ui/music/UploadPageModel.kt)），
`UploadPageModelTest` 钉住它：普通模式下 OK 只会勾选，只有在两个按钮浮出时才可能删掉东西。

### 3.3 上传到达时

新上传的文件放在曲库目录、并被**插到列表最前面**（顺序偏好里 prepend），所以"刚传的那首"就在第一行。
它的边框闪两下（亮度脉冲两个来回），并且列表会滚到顶部 —— 这两件事一起回答"传上来了吗"，
不需要用户去比对某个数字。闪的是刚到达的那一个 id：页面记住上一次读到的 id 集合，多出来的那个就是它。

### 3.4 从设置页回来

设置页的 `背景音乐` 与 `上传背景音乐` 两行都打开这个页面。Back 之后要回到**进去时的那个分页和那一行**，
而 `rememberSaveable` 做不到这一点 —— 打开子页面会把 home 整个从组合里拿掉。所以分页与最后按下的行
存在 `PositionKeys.SETTINGS_PANE` / `SETTINGS_ROW` 里（和列表位置记忆同一个机制），右侧分页的
`paneTop` 焦点请求也只挂在"记住的那一行"上。

## 4. 扫码上传：协议与实现

### 4.1 传输

电视上一个 `ServerSocket` 起的 HTTP/1.1 服务，**只在浮层打开时监听，Back 关闭即停**。
固定端口优先 `8123`（占用则顺延，端口写进二维码和那行地址）；不需要前台服务 —— 浮层开着时
Activity 必然在前台。`usesCleartextTraffic="true"` 已经在了，手机用 `http://` 直连即可。

路由（其余一律 404，且**任何情况下都不列目录**）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/u/<token>` | 吐出内嵌的 H5 页（assets 里的一个 html，无外链、无 CDN） |
| `POST` | `/u/<token>/up?name=<urlencoded>` | 请求体就是文件原始字节，落盘后 `200 {"ok":true}` |
| `GET` | `/u/<token>/state` | `{"count":N,"bytes":M,"limit":…}`，给 H5 显示"电视已经收到几首" |

`<token>` 是浮层打开时随机生成的一次性字符串，是唯一的凭据。只写曲库目录，落盘前对目标路径
做 canonical 校验（必须在曲库目录之内，防路径逃逸）。

### 4.2 限制

| 项 | 值 | 超限时 |
| --- | --- | --- |
| 单文件 | 40 MB | `413` + 中文原因（H5 上直接显示"这一首太大了"） |
| 曲库总量 | 1 GB（常量，管理页显示） | 拒绝并说明"删几首再传，或改上限" |
| 并发 | 1 | 第二个上传等前一个结束 |
| 类型 | 扩展名白名单 mp3/m4a/aac/flac/wav/ogg/opus **或** `audio/*` | 拒绝并说明 |
| 剩余空间 | 落盘前查 `StatFs` | 不足直接拒绝，不要写到一半才失败 |

文件名清洗：去掉任何路径分隔符与控制字符、限长（如 80 字符）、去重（同名加 `-2`）、保留中文。
落盘用"先写 `.part` 再改名"，避免半个文件进列表。

### 4.3 二维码

zxing `QRCodeWriter`（纠错级别 M）→ Compose 里画 Bitmap。编码内容是 `http://<ip>:<port>/u/<token>`，
`<ip>` 取**默认路由那个网卡**的 IPv4（有线/无线都可能有，取有网关的那个），并把同一个地址以文字显示。

### 4.4 安全边界

局域网内没有鉴权，token 就是凭据 —— 与图评同一个边界假设（README 的部署章节已写明"局域网是它的
设计边界"）。因此：服务只在浮层打开期间存在、只接受音频、有大小上限、只写一个目录、不提供任何读接口。

### 4.5 手机上看到的每一句话

手机上没有控制台，电视上也没有（README 的那条规矩）—— 所以每一条失败都要写成"下一步做什么"，
而不是一个状态。手机页面与电视浮层说的是同一件事的两种写法：

| 情况 | 手机页面上写的 | 电视面板上写的 |
| --- | --- | --- |
| 成功一首 | `已完成` + 进度条走满 | `✓ 曲名 · 大小` |
| 单首超过 40 MB | `这一首太大了（上限 40 MB），换一首或先压缩。` | `✗ 曲名 · 太大，已跳过` |
| 不是音频 | `只接受 mp3 / m4a / aac / flac / wav / ogg / opus。` | `✗ 曲名 · 不是音频，已跳过` |
| 曲库到 1 GB | `电视上的音乐已经满了，先在电视上删几首。` | `✗ 曲名 · 曲库已满` |
| 电视剩余空间不足 | `电视上没有足够的空间了。` | `✗ 曲名 · 电视空间不足` |
| 页面被关掉 / 连接断了 | `连接断了，回到电视上重新打开这个页面。` | — |
| 一首都没选 | `还没有选择文件` | — |

两条原则：手机页**不解释协议**（不出现状态码，只有一句下一步做什么），电视上**不出现单独成句的
"失败"**。H5 自带 zh/en 两套文案，按手机浏览器的 `navigator.language` 选。

## 5. 音乐从哪里来：一个目录

曲库目录（`getExternalFilesDir()/music`，取不到才退回内部 `filesDir/music`）是唯一的入口：

1. **手机扫码上传** —— §4，文件被复制进这个目录；
2. **用数据线或文件管理器拷进去** —— 一样会被列出来，因为列表就是"读这个目录"。

1.5.3 之前还有第三条：`扫描本机 / U 盘音乐`，走遍公共的 `Music`、`Download` 和每个挂载卷找音频，
找到的文件以**引用**的方式入列（就地播放、不复制）。它被删掉了，理由是实测 —— 在电视上用遥控器
按着去 U 盘里挑歌这件事没人会做，而手机上传就在同一个页面上、十秒钟能做完。它的代价却是实打实的：
两个存储权限（`READ_MEDIA_AUDIO` / `READ_EXTERNAL_STORAGE`）加一次授权对话框、一次"扫了才知道"的等待、
整整一类"文件被拔走了"的行，以及一条穿过删除路径的区分（哪些文件是"我们的拷贝"、哪些是"你的文件"）。
删掉之后，**manifest 里不再申请任何存储权限**。

拷贝进来的文件和上传的完全一样：出现在列表里、可以排序、可以勾选、`清空我的音乐` 会把它一起删掉
（它是这个目录里的一个文件，而那个按钮说的是"清空这个目录里的拷贝"）。

## 6. 播放

`SlideshowMusicPlayer` 从"只认 `asset:///`"改成"按条目给 URI"：内置还是 `asset:///`，自定义是
`Uri.fromFile(路径)`（`file:` 是曲库自己的前缀，不是 URI scheme，所以要剥掉再交给 `Uri`）。
音频焦点、`pause`/`stop` 的规则、`REPEAT_MODE_ALL` 都不动。

**tick 即生效 = 重新 `setMediaItems` = 从第一首重来**，这是现有行为，保持不变（D8 就是它的推论）。
正在放映时上传一首歌：入库、列表里立刻可见（音乐页的占用行也跟着变），但不替用户勾选 --
要听它，回到查看器的列表里按一下 OK。

## 7. 容量与清理

- 音乐页显示 `已用 / 上限`；超上限时上传被拒（507 + `library_full`）并说明
- 上传前查剩余空间（`StatFs`），不足直接拒绝（507 + `no_space`），不要写到一半才失败
- 单曲删除、`清空我的音乐`（只删上传进来的复制件；**引用**只从列表里去掉，绝不删源文件）
- 卸载即清；`设置 → 清除图片缓存` 不碰音乐（目录不同）

```
    MusicUploadProtocol.kt      纯逻辑：请求行/头解析、token、路由、体读取与上限、文件名清洗、地址选择
    MusicQr.kt                  zxing → BitMatrix（纯 JVM，可测）
  ui/music/
    MusicUploadScreen.kt         上传页：标题 + 二维码 + 带序号的列表（§3）
    MusicRowModel.kt            查看器列表的行模型（轨道 + 入口行）
    UploadPageModel.kt          行号、以及长按之后那三个模式的纯状态机
  ui/components/SettingsRows.kt InfoRow / ActionRow —— 从设置页提升出来，音乐页复用
  assets/music-upload.html      手机侧 H5（无外链、自带 zh/en）
```

- `MusicUploadProtocol` 与 `MusicRowModel` 是**纯 Kotlin**（不碰 Android API），所以 socket 之外、
  屏幕之外的一切都能进 JVM 单测 —— 这是 [DEVELOPMENT.md](DEVELOPMENT.md) 说的那条"把决策逻辑抽
  出来给测试"的做法。
- 用户音乐**永远不进 `assets/music/`**，所以 `SlideshowMusicTest` 那条"assets 里有文件不在目录中就构建
  失败"的反向检查（AGENTS.md 列为不可破坏项）不受影响，仍然有效。新增的 `music-upload.html` 在
  `assets/` 根下，不在 `assets/music/` 里。
- 新字符串进 `values/strings.xml` 与 `values-en/strings.xml` 两边。
- 版本：**1.5.0 / versionCode 26**。APK 从 25.7 MiB 长到 25.9 MiB，多出来的就是 zxing 的编码器。

## 9. 将来（明确不在这一版）

- **飞牛音乐库导入**：留的口子是一个 `MusicSource` 式的导入器 + "曲库目录是一等公民"。将来加它
  只需要多一个"把远程文件搬进曲库目录"的实现，列表、选择、播放都不改。
- 在线串流播放：不做，理由见 D1（要做得先有一份"断网也能立刻起播"的缓存策略）。
- SAF 系统文件选择器：不做 —— 电视上 D-pad 在这个系统界面里的体验很差，而且不少盒子根本没有
  DocumentsUI；用 U 盘 + 扫描替代。
- SMB / DLNA：不做 —— 依赖重、兼容坑多，收益不比 WebDAV 高。
- 逆向音乐 App 的私有接口：不做 —— 没有文档、随版本失效。

## 10. 风险与已知限制

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 手机连不上电视（AP 隔离、访客网络、跨网段） | 扫码上传整个不可用 | 浮层上就写出这条前提，并给出目录方案；不做静默失败 |
| 电视内部存储小（1–2 GB 可用） | 传不进去 | 上限 1 GB + 落盘前查剩余空间 + 上传用复制、本机用引用 |
| 各家盒子的存储与权限差异（Android 6–14、MIUI 电视） | 扫描结果不一致 | 扫描失败要说明是"没权限"还是"没有文件"；引用模式让 U 盘不受影响 |
| 省电策略杀掉监听线程 | 传到一半断 | 只在浮层期间监听，界面上写明"别离开这个页面"；`.part` 落盘不会留下坏条目 |
| 文件名含中文/emoji | 页面传参错乱 | 全程 URL 编码 + 落盘清洗，单测覆盖 |
| 内置四首是商业录音，公开分发有版权顾虑 | 长期合规问题 | 自选音乐上线后，内置曲目可以减到 0–1 首（APK 从 25.6 MB 降到 ~13 MB），这条限制随之消失 |
