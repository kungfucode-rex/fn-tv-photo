# 图评（Tuping）—— 照片评论服务的设计

> **状态：M1–M4 已实现（2026-10-09）。** 服务端（`server/`，Go）、H5 评论页、TV 端的二维码与弹幕层、
> `tools/mock-review` 契约测试都已落地并跑通；M5 的局域网真机验收、M6 的公网与小程序仍是计划。
> 本文是给"相册端集成者"看的协议文档，风格对齐 [fnos-photo-api.md](fnos-photo-api.md)，
> 并且仍然是协议、pHash 参数与短码规则的**唯一真相源** —— 实现与它不一致时，先改文档或改实现，不要两处各说各的。
> 目标读者：未来的我自己，以及任何想把二维码＋弹幕挂进自己相册的人。

## 0. 一句话

电视上预览一张照片时，角落出现一个二维码；客人用微信扫它，在手机上看这张图的缩略图、写一句评论；提交成功后，电视上评论以弹幕形式飘过。

相册端（FN Photo、以后的其它宿主）只做两件事：**上传缩略图换取短码**、**拉取评论并播放**。评论本体存在图评服务里，与相册彼此独立。

## 1. 已定的决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 第一版是**部署在 NAS 上的 Docker 容器 + H5 页面**，不做小程序 | 免备案、免审核、免成本，先把二维码/弹幕/实时链路跑通；协议按公网设计，第二阶段只换部署地址（§11） |
| D2 | 照片身份**分层**：`sha256(原图)` 精确优先，`pHash` 兜底 | 微信转发、截图、编辑、换 App 转存都会改变字节，单靠 sha256 会让评论裂成孤岛；单靠 pHash 又会误合并（§3） |
| D3 | 评论域默认"**图片域**"：全世界同一张图共享评论线程 | 氛围最大化；活动域（§4）作为第二阶段的补充，不是第一版的活 |
| D4 | 服务端用 **Go** | 单静态二进制、镜像约 20 MB、常驻内存约 20 MB；Windows 上交叉编译出 Linux 二进制 scp 到 NAS，NAS 上不需要任何运行时。代价是新增一套自包含工具链（§11） |
| D5 | **活动域只打通字段，不启用** | 表的列、API 的 `scope` 字段、二维码的来源从第一天就存在，但第一版恒为图片域；第二阶段加活动域 = 多一个来源 + 多一个过滤条件，不改表、不改协议（§4） |
| D6 | 服务端与相册端**同一个仓库**，代码在 `server/`（独立 `go.mod`） | 协议、pHash 参数、短码规则在早期天天改，一次提交能同时改协议文档、TV 端、服务端和 mock；`settings.gradle.kts` 只 `include(":app")`，两边互不可见。拆分触发条件与成本见 §11.2 |

### 1.1 第一版明确不做的事

小程序码、微信登录、云开发、备案、域名、CDN、内容安全云接口、审核台、**活动域的启用**（字段仍然打通，见 D5）、点赞弹幕。全部推到第二阶段。

## 2. 为什么是这个形状：三个真正的难点

二维码和弹幕是这个项目里最简单的部分。难的是另外三件事，它们决定了后面所有的设计。

### 2.1 "所有相册都集成图评"短期做不到

小米相册、威联通 QuMagie、飞牛相册都是闭源且没有插件体系的，无法让它们渲染二维码或弹幕。能挂上图评的宿主只有三类：

| 宿主 | 可行性 | 说明 |
| --- | --- | --- |
| 自己能改代码的 App | 高 | FN Photo，第一版的参考实现 |
| **网页版**相册（fnOS Web、群晖 Photos Web） | 高 | 油猴脚本注入 DOM，是"让别人的相册立刻用上"的最快路径 |
| 截屏 + 悬浮窗的"图评层" | 低 | MediaProjection 截图 → pHash → 悬浮窗弹幕。可行但耗电、体验差，最后手段 |

所以图评的形态是 **协议 + 参考实现 + 一个通用宿主**。战略重点在第三条：把 FN Photo 从"飞牛客户端"扩成"电视上的多源相册"（飞牛 / WebDAV / SMB / 群晖 / 本地），**自己当那个相册**，而不是等别人集成。

### 2.2 小程序看不到 NAS —— 缩略图必须由相册侧上传

手机在 4G 下不可能、也不该访问家里的 NAS。所以"小缩略图"不是可选字段，它同时承担两个职责：

1. 小程序/H5 里给人看的预览；
2. 服务端计算 pHash 的输入。

**服务端收到任何上传的图片都强制重新解码再编码一遍，绝不原样落盘**——因为微信"原图"是保留 EXIF/GPS 的（"发原图暴露家庭住址"说的就是这件事），上传方永远不知道自己送来了什么。

### 2.3 图片域 = 服务端天然是一台"以图搜图"的机器

默认图片域意味着任何拿到同一张图的人都能读到这条评论线程，也意味着别人可以用它判断"某张图有没有人评论过 / 是否在别人库里"。这是这个组合必付的代价，只能收敛，不能消除（缓解清单见 §12）。

## 3. 身份：分层多指纹

### 3.1 两种指纹的分工

| | `sha256(原图字节)` | `pHash`（缩略图） |
| --- | --- | --- |
| 判据 | 字节完全相同 | 看起来是同一张 |
| 计算位置 | 相册侧（要读到原图） | 服务端（收到缩略图就能算） |
| 成本 | 读一遍原图字节 | 解码 320px + 缩放到 32×32 + DCT，几百微秒 |
| 漏判 | 多：转发、截图、编辑、转存都会变字节 | 少 |
| 误判 | 无 | 有：连拍、纯色背景、截图 |

**身份始终是服务端的 `image_id`（ULID）**，两种指纹都只是索引。原因：pHash 有损（会误判）、可逆（能反推出符合某个哈希的图，**绝不能当 URL key 或鉴权凭证**）、算法会升级（所以 `phash_version` 是必存字段）。

### 3.2 匹配流程

```
POST /v1/photos 带 thumb（必须）+ sha256Original（可选）
  │
  ├─ 预处理：解码 → 检测并剥掉纯色边框（§15.1 实测：不剥，同一张图会变成两个身份）
  │
  ├─ sha256Original 非空？
  │     ├─ 查 photos.sha256 命中 → 挂到那个 image_id      matched="sha256"
  │     └─ 未命中 → 落到 pHash 分支，并把 sha256 写进新记录
  │
  └─ pHash 分支（从预处理后的缩略图计算 phash = pHash64 ‖ dHash64）
        ├─ 候选集：画幅比例与本次相差 ≤2% 的照片
        ├─ 对每个候选分别算 pHash 段与 dHash 段的汉明距离
        ├─ pHash ≤6 且 dHash ≤6 且 双方 variance ≥ 500 → 挂上   matched="phash"
        ├─ pHash 7–11                                  → 新建 + 记一条"疑似"关系，等带 sha256 的一方来认领
        └─ 其余                                        → 新建    matched="new"
```

### 3.3 护栏参数（第一版取值，上线后按真实数据调）

| 参数 | 取值 | 作用 |
| --- | --- | --- |
| 画幅比例容忍 | ±2% | 裁剪过的图不该进候选集 |
| pHash / dHash 阈值 | **各 ≤6 / 64 位** | §15.1 实测：真匹配最坏 4，最近的真不同样本 12 — 6 落在中间，两侧都有余量。原先定的 4 太紧，会把"服务端剥掉黑边后"这种正常情况判成两张图 |
| 疑似区间 | pHash 7–11 | 只记关系，不自动合并 |
| 低方差图 | variance < **500**（64×64 灰度方差）不参与**自动**合并 | §15.1 实测：真照片 4377–6804，扁平图 0 —— 而且**所有扁平图互相距离为 0**，不挡就会成团错误合并 |
| 黑边剥离 | 只剥**对称**且**近黑（均值 ≤8）或近白（≥247）**的边，而且只作为**追加候选**（剥与不剥各算一份指纹，任一命中即同一张） | §15.1 实测：补边到 16:9 把距离推到 43，剥掉后回到 6。但 §15.2 实验 2 发现，naive 的剥离器会把"照片里本来就有的浅色边"（均值 243）一起剥掉，反而把 0 位的匹配推到 17 —— 剥边必须限制在 padding 的特征上 |
| 联合判据 | `pHash64 ⊕ dHash64` 共 128 位 | 单用 64 位在千万级图库下会出现假配对 |
| 规范缩略图 | 320px 宽、**等比、不裁剪**、EXIF 全剥 | pHash 归一化到 32×32，尺寸无所谓，**裁剪会废掉它**：§15.1 实测裁剪到 16:9 造成 54 位，和"另一张照片"（54）一样远 |

> ✅ 已实测（§15.2 实验 2）：飞牛的 `m` 档**等比保比例**，规则是"短边上限 **1280**、不放大小图" —— 3000×4000 的竖图拿回来是 1280×1707，四个角标记完整、无裁无补，与原件（3000×4000）的指纹距离 **2/128**，远在阈值 6 之内。规范缩略图可以直接用 `m`，注册一张照片不需要先下原图。另：`o` 档就是上传的原文件字节（sha256 完全一致）。

### 3.4 合并必须可逆

`photos.merged_into` 指针 + 查询时跟随指针（union-find 语义），**评论不搬家**。一次误合并就是一次数据事故，而搬家式的合并连解绑都会丢评论。

- 合并记录留在 `merges` 表里（from / to / reason / 汉明距离 / 时间）。
- 提供"这不是同一张照片"的解绑入口。
- 相册主人对自己的照片有解绑权。

### 3.5 sha256 什么时候算

只在**原图已经在磁盘缓存里**时算：FN Photo 的幻灯片取原图模式、或用户按了"原图"按钮时顺手算，零额外流量。其余情况只用已有的 `m` 档缩略图（短边上限 1280，本就在查看器的磁盘缓存里，§15.2）走 pHash 分支——**绝不为了算哈希去下载一张几十兆的原图**。

飞牛的 `o` 档**就是上传的原文件字节**（§15.2 实验 2 实测：sha256 完全一致，逐像素最大差 0），所以这里算出的 sha256 与"同一份原文件在别处被索引"时算出的是同一个值——这正是分层方案里 sha256 那一层要覆盖的场景。

## 4. 评论域

| 域 | 语义 | 第一版 |
| --- | --- | --- |
| 图片域 `image` | 全世界同一张图共享一条线程 | ✅ 默认 |
| 活动域 `event` | 评论只属于某一场活动（婚礼、年会、同学会） | 第二阶段 |

数据模型里两者从一开始就并存（`scope_type` / `scope_id`），第一版只写 `image`。**协议里也一样**：`/v1/photos` 从第一天就收 `scope` 字段（相册端恒送 `image`），`/v1/photos/{code}` 的响应里带上 scope——所以第二阶段加活动域不需要改表、不需要改协议，只需要多一个二维码来源和相册端的一个作用域选择。

活动域的价值在于：它是隐私上安全得多的模式，而且现场感更强——同一个相册在婚礼上投影和在家里回看，评论不该混在一起。

### 4.1 多实例：自托管实例与官方实例是两回事

图评是"谁想部署就自己部署一份"的软件（§11.5），所以这里必须把两件事分开说：

| | 自托管实例 | 官方公共实例 |
| --- | --- | --- |
| 数据库在哪 | 部署者自己的 NAS | 作者托管 |
| 评论范围 | **只有连到这个实例的相册看得见** | 连到它的所有相册共享 |
| 数据所有权 | 部署者自己备份、自己删 | 作者 |
| 典型用途 | 家里、公司、一场婚礼 | D3 说的"全世界同一张图共享" |

**"图片域"要读准：它是"同一个实例内的同一张图共享"，不是跨实例共享。** 跨实例共享需要联邦——实例之间互信、去重、身份、审核、滥用处理——那是另一个量级的工程，第一版和第二版都不做。

所以 D3 的"全世界"实际上取决于**有没有一个官方实例**：

- 只有自托管时，每个部署者拿到的是一个**私有的图片域**。这本身就很有用（家庭聚会、婚礼、公司年会），但"陌生人给同一张图留言"不会发生。
- 要真的全世界共享，就得有一个公共实例作为唯一事实来源。TV 端接哪个实例只是一个设置项，两种模式共用同一条代码路径。

### 4.2 官方实例：第一版不建，边界先划清

**决策：M1–M5 不做官方实例。** 自托管先跑通；官方实例只有在真有第二个用户时才值得运维——它带来的是服务器成本、备案、内容审核、滥用处理和法律暴露，而收益在只有作者一个人用时是零。

**如果将来要开，清单是这些**（不是"部署一下就行"）：

| 项 | 内容 |
| --- | --- |
| 域名与备案 | 公网 HTTPS，国内节点需要备案；小程序路线还要小程序自己的备案（§10.2） |
| 内容安全 | `msgSecCheck` + 敏感词 + 举报入口 + 人工删除；UGC 的合规义务不因为"只是个弹幕"而消失 |
| 反滥用 | 每 IP/每身份限流、图片上传配额、缩略图 TTL、定期清理 |
| 运维 | 每日备份（SQLite `.backup` + 缩略图）、磁盘水位告警、日志留存 |
| 法律 | 隐私政策、用户协议、侵权投诉与"通知—删除"通道 |

**边界（明确不做的）**：不做联邦（实例之间不互通，§4.1）；不做账号体系；不做跨实例同步；官方实例只承载"图片域"这一种线程。

**两个必须说清楚的用户预期**：

1. 自托管实例的评论**搬不到**官方实例（数据在各自的库里），换实例只是改一个设置项，线程从零开始。
2. 官方实例一旦存在，它就是**唯一事实来源**：同一个哈希的评论都在那里，别人的自托管实例看不到它们——除非那个人也把 TV 指向官方实例。

**什么时候开**（触发条件，任一成立）：

- 有 3 个以上外部部署者问"怎么和别人共享同一张图的评论"；
- 你自己需要在公网用（比如在父母家的电视上扫自己家的照片）；
- 有第二个用户在真实场景里用起来，并且他愿意把评论放在你的服务器上。

## 5. 数据模型

SQLite（WAL），足以撑到十万级照片。DDL 草案：

```sql
CREATE TABLE photos (
  id               TEXT PRIMARY KEY,        -- ULID
  sha256           TEXT,                    -- 原图字节；可空
  phash            BLOB NOT NULL,           -- 16 字节：pHash64 || dHash64
  phash_version    INTEGER NOT NULL,
  width            INTEGER NOT NULL,
  height           INTEGER NOT NULL,
  variance         INTEGER NOT NULL,        -- 规范缩略图的方差
  thumb_key        TEXT,
  thumb_expire_at  INTEGER,
  comment_count    INTEGER NOT NULL DEFAULT 0,
  visibility       INTEGER NOT NULL DEFAULT 1,  -- 0 私密 / 1 图片域 / 2 关闭评论
  owner_token_hash TEXT,
  merged_into      TEXT REFERENCES photos(id),
  first_seen_at    INTEGER NOT NULL,
  last_seen_at     INTEGER NOT NULL
);
CREATE INDEX idx_photos_sha256 ON photos(sha256);
CREATE INDEX idx_photos_ratio  ON photos(width, height);

CREATE TABLE codes (
  code       TEXT PRIMARY KEY,              -- 6 位 base62，不可枚举
  image_id   TEXT NOT NULL REFERENCES photos(id),
  scope_type INTEGER NOT NULL,              -- 1 image / 2 event
  scope_id   TEXT,
  created_at INTEGER NOT NULL,
  expires_at INTEGER
);

CREATE TABLE comments (
  id           TEXT PRIMARY KEY,            -- ULID
  image_id     TEXT NOT NULL REFERENCES photos(id),
  scope_type   INTEGER NOT NULL,
  scope_id     TEXT,
  content      TEXT NOT NULL,               -- ≤20 字（一条弹幕在电视上能显示的长度，§9.5）
  nickname     TEXT NOT NULL,               -- ≤12 字
  avatar_url   TEXT,
  openid_hmac  TEXT,                        -- 小程序来源
  anon_id      TEXT,                        -- H5 来源（设备 cookie 的 HMAC）
  status       INTEGER NOT NULL DEFAULT 1,  -- 0 待审 / 1 可见 / 2 屏蔽 / 3 删除
  report_count INTEGER NOT NULL DEFAULT 0,
  ip_hmac      TEXT,
  client       TEXT,                        -- "h5/1" | "mp/1"
  idem_key     TEXT,
  created_at   INTEGER NOT NULL,
  UNIQUE(image_id, idem_key)
);
CREATE INDEX idx_comments_image ON comments(image_id, created_at);

CREATE TABLE merges (
  from_image_id TEXT PRIMARY KEY REFERENCES photos(id),
  to_image_id   TEXT NOT NULL REFERENCES photos(id),
  reason        TEXT NOT NULL,              -- sha256 | phash | manual
  score         INTEGER,                    -- 汉明距离
  created_at    INTEGER NOT NULL
);

CREATE TABLE events (                       -- 第二阶段
  id TEXT PRIMARY KEY, name TEXT,
  created_at INTEGER NOT NULL, expires_at INTEGER,
  owner_token_hash TEXT
);

CREATE TABLE rate_limits (key TEXT PRIMARY KEY, window_start INTEGER, count INTEGER);
```

设计要点：

- **缩略图不进评论行**。它是照片的属性；100 条评论存 100 份图是错的。
- `openid` / `ip` 只存 HMAC，DB 泄露也不泄露用户标识。
- `idem_key` 让"提交按钮点了两次"只产生一条评论。
- `comment_count` 冗余计数，列表页不必 COUNT。

### 5.1 pHash 的检索

不搞 BK-tree：起步阶段直接全表扫——16 字节 × 100 万行 ≈ 16 MB，Go/Kotlin 里几毫秒。真到了卡的程度，再按"64 位切成 4 个 16 位块、候选必须有一块在距离内完全匹配"做多索引。

## 6. 协议 `/v1`

### 6.1 端点

| 方法 | 路径 | 谁用 | 说明 |
| --- | --- | --- | --- |
| POST | `/v1/devices` | 相册端 | 申请设备令牌与 owner token（§7）；首次运行时一次 |
| POST | `/v1/photos` | 相册端 | 注册照片，返回 `imageId` + 短码 + 二维码地址 |
| GET | `/v1/qr/{code}.png` | 相册端 | 二维码 PNG（服务端生成并缓存，TV 只下图，不引 zxing） |
| GET | `/v1/photos/{code}` | H5 / 小程序 | 缩略图签名 URL + 评论数 |
| GET | `/v1/comments` | 相册端 | 按 `imageId` + `since` 拉增量 |
| POST | `/v1/comments` | H5 / 小程序 | 提交评论（幂等 + 内容安全 + 限流） |
| POST | `/v1/comments/{id}/report` | H5 / 小程序 | 举报 |
| DELETE | `/v1/photos/{id}` | 相册端（owner token） | 删图 + 全部评论 + 缩略图 |
| GET | `/v1/admin/comments` | 管理员 | 审核队列（令牌、`?token=`，或网页登录后的 cookie） |
| GET | `/admin` | 管理员 | 登录表单；已登录时是"已经登录"页（§17.15） |
| POST | `/admin` | 管理员 | 用 `TUPING_ADMIN_TOKEN` 换一个签名 cookie，303 回原页 |
| POST | `/admin/logout` | 管理员 | 退出。POST 而非 GET：GET 的退出能被别的页面的 `<img>` 触发 |
| GET | `/c/{code}/edit/{id}` | 管理员 | 改一条评论的表单 |
| POST | `/c/{code}/edit/{id}` | 管理员 | 保存这次修改，303 回照片页 |
| POST | `/c/{code}/delete/{id}` | 管理员 | 软删除一条评论（`status=3`），303 回照片页 |
| WS | `/v1/live/{imageId}` | 相册端 | 实时弹幕推送 |
| GET | `/healthz` | — | 存活 |

### 6.2 注册照片

```http
POST /v1/photos
Content-Type: multipart/form-data
X-Device-Id: <设备 ULID>
X-Device-Token: <设备令牌>

thumb: <320px 宽、等比、JPEG q80 的字节>
meta:  {"localId":"1015","source":"fnos","sha256Original":null,"width":4032,"height":3024}
```

`X-Device-Id` / `X-Device-Token` 来自 `POST /v1/devices`（§7）：相册端首次运行时申请一次，之后
存在 `SettingsStore` 里。相册端不自己造设备 id —— 服务端发的才是它认得的那一个。

```json
{
  "imageId": "01J...",
  "code": "7fKq2a",
  "matched": "sha256",
  "qrUrl": "http://192.168.31.14:8080/v1/qr/7fKq2a.png?size=440",
  "thumbUrl": "http://192.168.31.14:8080/t/7fKq2a.jpg?sig=...&exp=...",
  "commentCount": 3
}
```

`matched` ∈ `sha256 | phash | new`，相册端只用来记日志，不参与逻辑。

**同一设备重复注册同一张照片**（`source + localId` 相同、且 `last_seen_at` 在 N 天内）直接返回既有结果，不重复上传缩略图——这就是电视上"预注册"的成本控制手段。

### 6.3 拉评论 / 收弹幕

```http
GET /v1/comments?imageId=01J...&since=1730000000000&limit=50
```

```json
{
  "serverTime": 1730000123456,
  "items": [
    {"id":"01J...","nickname":"小王","content":"这张好看","createdAt":1730000000123,"status":1}
  ]
}
```

WebSocket `/v1/live/{imageId}` 推同一个结构，让弹幕层只有一种输入：

```json
{"t":"comment","id":"01J...","nickname":"小王","content":"这张好看","createdAt":1730000000123,"status":1}
{"t":"ping"}
```

这条消息带的是评论的**状态**，不只是"来了一条新的"：编辑、待审、屏蔽、删除都把同一条消息再发一遍，`status`
换成新值（§17.17）。所以客户端的规则只有一条——按 id 覆盖手里的那份。`status` 因此不能省：`0` 是真实状态
（待审），字段缺席和执行 `optInt("status", 1)` 的客户端会把一条已下架的评论读成可见。

### 6.4 提交评论

```http
POST /v1/comments
Content-Type: application/json

{"code":"7fKq2a","content":"这张好看","nickname":"小王","idemKey":"<客户端 UUID>","anonId":"<H5 设备 cookie 的 HMAC>"}
```

```json
{"id":"01J...","createdAt":1730000123456,"status":1}
```

`status` 为 `0` 时 H5 页面要如实说明"已提交，审核后显示"，而不是假装成功——这是"结论能信到什么程度"的问题，和这个仓库其它地方的规矩一致。

### 6.5 错误

```json
{"error":{"code":"rate_limited","message":"发得太快了，歇一会儿"}}
```

错误码：`bad_request` / `not_found` / `rate_limited` / `content_rejected` / `too_long` / `photo_locked` / `unauthorized` / `server_error`。

## 7. 账号与权限

| 身份 | 来源 | 权限 |
| --- | --- | --- |
| 设备令牌 | 相册端首次运行时申请，存在 `SettingsStore` | 注册照片、读评论、删自己的照片 |
| owner token | 注册照片的设备持有 | 删图、解绑合并、屏蔽评论 |
| `openid_hmac` | 小程序 `code2session` | 发评论、举报（第二阶段） |
| `anon_id` | H5 首次访问时下发的 cookie 的 HMAC | 发评论、举报（第一版） |
| 管理员令牌 | 环境变量 `TUPING_ADMIN_TOKEN`，网页登录时用它当口令 | 审核队列、全局删除、网页上的编辑／删除（§17.15） |

限流（第一版取值）：

| 维度 | 限制 |
| --- | --- |
| 单 `anon_id` / `openid` | 5 条/分，50 条/天 |
| 单 IP | 30 条/分 |
| 单张图 | 200 条/小时（防刷屏） |
| 单设备注册 | 300 张/小时 |
| **整个发评论端点** | **120 条/分**（2026-10-11 加，见下） |

前三行都是**按调用方**算的，而按调用方算的额度全都可以靠"换一个身份"绕开：清掉 `anon` cookie 就是新访客，换一个出口 IP 就是新地址，换一张照片就是新图。公网部署上这是实际发生的事，所以端点本身需要一个自己的额度：**整个服务每分钟最多受理 120 条新评论**，`store.LimitPerService`，键是固定的 `cmt-service:min`，`handleCommentCreate` 与 H5 表单（`handlePageSubmit`）共用同一个键——两条路创建的是同一种东西，只数其中一条等于只封了半个服务。它同时也是所有额度里**最松**的一档，因为它也是唯一会误伤正常用户的：全局 2 条/秒，家庭聚会到不了；单个人刷屏仍然由每 IP 30/分 和每个访客 5/分 先拦住。检查顺序上它排在第一位，这样"服务满了"这种与调用方无关的拒绝不会顺带扣掉调用方自己的额度。`TestCommentBudgetIsWholeService` 是唯一能看见它的形状：五个回环源地址（每个各自 30/分的 IP 额度）、每条请求都换一个 `anonId`（每个访客各自 5/分），谁都没有超自己的线，端点仍然在第 121 条上拒绝。

## 8. 内容安全

第一版（局域网自托管）：长度 ≤20 字、5 分钟内同图同内容去重、过滤 URL / 手机号 / QQ 号 / "加微信"这类广告模板、本地分级敏感词表（直接拒 / 进待审）。

**长度上限是 20 字而不是 80（2026-10-11 改）。** 上限的原意是"人写得出来、服务端拦得住"，但一条弹幕在电视上只能占屏幕宽度的 45%（§9.5 的上限，用来把最长一条的横穿时间压在照片的停留时间里），1080p 下就是 864px；弹幕层的最大字号是 40px，一行约 21 个汉字。80 字里有五六十个字**永远显示不出来**，只会变成省略号——手机在邀请人打一段在电视上读不到的话。20 字在最大字号下仍是 800px，留出了宽字形（emoji 占一个 rune pair、宽度还超过一个汉字）的余量。已经在库里的长评论不受影响，它们照旧被 45% 上限截断。

第二阶段（公网 + 小程序）：**必须**接入 [`msgSecCheck`](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_msgseccheck.html)，这是小程序审核的硬要求，不是可选项。加上人工审核台和举报闭环。

## 9. 客户端一：FN Photo（电视端）

### 9.1 落点

- **二维码位置：左下角、信息条上方。** 右下角已经被翻页箭头（`ViewerScreen` 的 `Alignment.BottomEnd`，`bottom = 132.dp`）+ 幻灯片按钮 + 向上展开的设置行占满了；左下角只有一块静态 `InfoText`，没有交互冲突。
- 二维码要**静态、高对比、带白底留白区**，1080p 下 ≥200px（约屏高 20%）。白底留白按规范留 **4 个模块**（200px 的码约 24px 边距；§15.2 的实验素材就是这么做的）。**不要做呼吸/淡入淡出之类的动画**——正在扫的时候动一下就扫不到了。每张图淡入 8 秒后淡出，信息条打开时常显，视频不显示。
- 新增 `data/review/`：`ReviewClient`、`PhotoIdentity`、`ReviewRepository`、`DanmakuFeed`。
- **必须是独立的 OkHttp 客户端**：绝不能复用 NAS 那个"首次使用即固定证书"的客户端，否则图评服务器的正常证书会被 pin 检查拒掉。

### 9.2 预注册

像 `ImagePrefetcher` 那样，对当前 + 后面若干张提前上传规范缩略图换短码，并缓存短码与二维码 PNG。客人扫的时候码已经在手，不必等一次网络往返。

### 9.3 失败必须静默

图评服务器连不上时，二维码和弹幕整层消失，**绝不影响看图**——和"翻页绝不清空屏幕"是同一条原则。日志里记一行，设置页里可以看状态。

### 9.4 设置项

`图评（关 / 仅幻灯片 / 全部）`、`服务器地址`、`上传范围（当前相册 / 全部）`，再加一行 **图评连接状态**：当前是否连得上、用的是哪个地址、最后一次失败的原因。电视上没有控制台——"连不上服务器"必须能在屏幕上读出来，这和设置页里 **上次崩溃** 那一行是同一个理由。

**这一行要回答两个问题，不是一个**（§17.7）：服务器在不在（`/healthz`，不需要鉴权），以及**它认不认这台电视的设备令牌**（一次带令牌的探针）。只答前者的后果是实打实的：服务端重装过、数据库重建过、电视上的地址改到另一台服务端之后，`/healthz` 照样 200，这一行显示绿色的"已连接"，而注册照片全部 401——图评整层画不出来，按钮还是灰的。

`SettingsStore` 里加一个字符串 + 几个枚举即可，不必引入 Room。

**上传范围默认关闭**：浏览相册不等于同意把整个图库传上服务器。

### 9.5 弹幕规格

**传输**：进入某张图时 HTTP 拉一次历史，随后 WebSocket 订阅新评论；WS 断开降级到 5 秒轮询，再断就静默停下。**任何一层不可达都不影响看图。**

**渲染**：自己写，不用 DanmakuFlameMaster（View 时代、已停维护）。Compose 里的做法是**帧驱动的 draw-phase 偏移**：一个 `withFrameNanos` 循环更新 `MutableState<Long>`，每条弹幕一个 `graphicsLayer { translationX = ... }`，只走 draw phase，不触发重组/重排；文字宽度用 `TextMeasurer` 量一次并缓存；轨道尾端离开屏幕右侧才允许下一条进入同一轨。低端电视盒子上这一条决定了弹幕是流畅还是卡成幻灯片。

**具体参数（1080p 基准）**：

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 速度 | 恒定 **220 px/s**（横穿 8.7 秒） | 恒定速度才可读；不随幻灯片间隔变。原设计是 320（6 秒），实机看了两轮都说快，见 §17.10 |
| 最长一条 | 屏宽 **45%**（864px：约 25 个汉字 @34px、21 个 @40px），超出截断加省略号 | 再长就要 12.7 秒才走完，超过一次停留能给的时长。评论本身的上限已经收到 20 字（§8），所以这条现在只给库里已有的长评论兜底 |
| 字号 / 描边 | **34px**（少）/ **40px**（多）白字 + 3px 黑描边，**单位是真机像素** | 照片明暗不定，描边是唯一在所有底图上都可读的做法。字号必须按像素算，不能当 `sp` —— §17.8 那个"只剩两个字加省略号"的 bug 就是这里 |
| 行 | **按行轮流**（上一条进过哪一行，下一条从下一行起试）；一行里后一条要等前一条尾部让开 **200px≈0.9 秒** | 一行承载多条，但"不能挨得太紧"。两种错法都记在 §17.10：只挑最低可用的那行会把所有弹幕压成一行；而"空行优先"又变成一条评论一行（5 条评论 5 行） |
| 行区间 | 从顶部安全区 **96px** 起，到**全屏高度的 1/4（少）或 2/5（多）**为止；文字在各自行内垂直居中 | "2 行最多在顶部占全屏 1/4 的高度，4 行最多占 2/5"。区间按**整屏**比例算，否则"占多少屏幕"无从检查（旧的固定区间 96–700 让两行下探到 528px，占了半屏） |
| 同时在上限 | **2 行（少）/ 4 行（多）**；一行满了就排队，队列上限 50 条，再溢出丢最旧 | 电视的 GPU 和眼睛都有上限 |
| 开场重播 | 进入某张图时取最近 **8** 条，**错峰 1.2 秒一条**播一遍 | 让人知道"这张有人说过话"，但不要一次涌出来 |
| 循环 | 之后**不停地轮转**这张图的评论，每 1.2 秒轮到下一条 | 一张停留一分钟的照片不该在头几秒之后就静下来 |
| 重复下限 | 同一条**间隔不小于 5 秒**（`DanmakuFeed.REPEAT_COOLDOWN_MS`），换图清零 | 循环要有下限才叫循环；没有它就是同一条来回抖 |
| 三档设置 | `关 / 少 / 多`，默认 **少**；一个值同时管字号、**行数**、开场重播条数 | 别给三个独立开关——§9.4 的规矩 |
| | **少**：字号 34、**最多 2 行**、重播最近 3 条 | |
| | **多**：字号 40、**最多 4 行**、重播最近 8 条 | |
| 视频 | 不显示弹幕 | 和二维码一致；视频有自己的画面节奏 |

**与幻灯片间隔的冲突（3 秒间隔 vs 最长 13.7 秒的弹幕）**：解法是**新评论到达时把当前照片的停留延长**，延到"那一条走完 + 1 秒"，上限 **+6 秒**，做成一个默认开启的开关。这比"按间隔压缩速度"好：压缩后 3 秒横穿屏幕的弹幕没人读得完，而"有人说话了，这一张多停一会儿"本身就是想要的效果。开关关掉时接受截断。速度降到 220 之后这条冲突更紧了一格：默认 **8 秒 + 6 秒 = 14 秒**刚刚够最长的一条（12.7 + 1），而 **3 秒间隔那种组合装不下**——那时照片照常前进、那条弹幕没走完就被换掉，这是"再慢一点"换来的、明确接受的代价。

**两条硬规矩**：

- 弹幕层**绝不抢遥控器焦点**，也不改变信息条/设置行展开时的按键语义（不可聚焦、不吃按键）。
- 信息条里显示 `评论 N` —— 它和二维码是同一份数据的两个出口，有评论而二维码被关掉时，这一行是人唯一能知道的途径。

## 10. 客户端二：H5（第一版）与小程序（第二阶段）

### 10.1 H5 规格（第一版）

二维码内容就是 `http://<NAS-IP>:8080/c/{code}`，微信扫一扫在微信内置浏览器里打开。

**形态：纯服务端渲染的一页，页面里没有一行 JavaScript。** 缩略图、已有评论、表单在一次响应里出来；提交走普通 `POST` + **303 重定向回同一页**（PRG 模式）。这样"双击提交""刷新重提""打了一段话结果网络断了"这三类经典问题都不需要前端逻辑，页面也只剩一个文件、零外部资源、不到 20 KB——局域网和弱网下最快的那种。字数上限用 `maxlength` 属性，不用 JS 计数器。

| 项 | 决定 |
| --- | --- |
| 页面内容（自上而下） | 缩略图 → **表单（昵称 + 评论 + 提交）** → 已有评论（最近 20 条，相对时间由服务端按响应时刻算，超 24 小时显示日期） |
| 缩略图 | 320px 宽、签名 URL（10 分钟有效）；**不显示任何元数据** —— 相册名、拍摄时间、位置一概不显示 |
| 昵称 | 可选，≤12 字，留空存为 **"匿名"**；填过的由服务端记在 `tuping_name` cookie 里，下次预填（页面没有 JS，`localStorage` 做不到这件事）——见 §17.11 |
| 评论 | ≤20 字（电视上一行能显示的长度，§8），服务端也校验；过滤 URL / 手机号 / QQ 号（§8） |
| 身份 | 首次访问下发 `anon` cookie，服务端只存它的 HMAC（§7）；用于限流与"我发过的" |
| 提交后 | 303 回 `?ok=1`：顶部一条"已提交"，自己那条高亮在列表顶部；若落到 `status=0`（待审）则明确写"已提交，审核后显示"——**不假装成功** |
| 失败 | **保留用户已经打的字**，原因写在输入框上方（太快了 / 太长了 / 被拒绝 / 服务器不可达） |
| 举报 | 接口保留（§6.5、§14 的"第三次举报转待审"照旧可测），但**页面上不再放那一行链接**（§17.11）：直接用 `/c/{code}/report/{id}` |
| 管理员 | 页脚一行 **管理员登录** 通向 `/admin`（只在服务端设了 `TUPING_ADMIN_TOKEN` 时出现）。登录后页顶一条"管理员模式"，每条评论下面多出 **编辑** 与 **删除**：编辑是一张单独的页面（`/c/{code}/edit/{id}`），删除是一次 POST（软删除）。**这一页仍然一行 JavaScript 都没有**（§17.15） |
| 样式 | 跟随系统 `prefers-color-scheme`；正文与输入框字号 ≥16px（iOS 会自动放大更小的输入框） |
| 混合内容 | 页面里**不能引用任何 https 资源**——局域网是明文 http，混用会被浏览器拦掉。反向同理：页面走 https 时不能引用 http 的图，所以地址必须跟着连接走（§17.23） |

- **待验证**：微信内置浏览器打开局域网明文 `http://192.168.x.x` 是否正常（§15 实验 1）。这个结论决定第一版是"扫一扫直接写"还是"得换浏览器"。
- 安全边界：**这个容器绝不能把端口映射到公网**。它是为局域网设计的，没有任何面向公网的加固。

### 10.2 小程序（第二阶段）

| 项 | 结论 |
| --- | --- |
| 扫码入口 | **小程序码**（`getUnlimitedQRCode`）：微信扫一扫直开小程序。`scene` 最多 **32 个可见字符**，所以二维码里只能放短码——这也顺带解决了"哈希不该出现在 URL 里"的问题 |
| 备用入口 | URL Link / Short Link 的普通二维码：任意相机可扫，但有配额和有效期 |
| 身份 | `wx.login` → `code2session` → `openid`（只存 HMAC）；昵称头像用"头像昵称填写能力"，`getUserProfile` 已废弃 |
| 内容安全 | 提交前过 `msgSecCheck`；图片评论过 `mediaCheckAsync` |
| 免域名备案 | 小程序端用云开发/云托管的 `wx.cloud.callContainer`，不需要自备备案域名，也不用配 request 合法域名；电视端走云托管公网域名或自有域名 |
| 备案 | 小程序自 2023-09 起必须完成备案才能上架（[参考](https://m.sohu.com/a/710496070_99900743/)） |
| **类目风险** | 图片评论可能被归到"社交-社区/论坛"，据现有资料该类目基本要求企业主体 + 资质，个人主体大概率开通不了（[相关讨论](https://wxopen.club/topic/5e2eb1f5f2cd9aae7acbc36e)）。**这是整个小程序路线最大的单点风险，必须先去微信开放社区确认。** |

## 11. 服务端与开发环境（Go）

### 11.1 语言与依赖

服务端用 **Go**（D4）。选它的理由只有一条是决定性的：这台服务要在一台 NAS 上一天 24 小时跑很多年，而 Go 交出来的是一个静态二进制——镜像约 20 MB、常驻内存约 20 MB、不需要任何运行时。Kotlin/Ktor 也能做，代价是 180 MB 起的 JRE 基础镜像和 200 MB 起的常驻内存。曾以为"Kotlin 可以和 `app/` 共享协议模型"是 Ktor 的一个优势，但它站不住：`FnApi.kt` 用的是 `org.json` 手工解析（这个仓库的既定风格），而 pHash 只在服务端算，两端本来就没有多少可共享的代码。

这几个必需的库都是纯 Go，交叉编译不需要 cgo：

| 用途 | 选型 |
| --- | --- |
| 二维码 PNG | `github.com/skip2/go-qrcode` |
| pHash / dHash | `github.com/corona10/goimagehash` |
| SQLite | `modernc.org/sqlite`（纯 Go，无 cgo） |
| WebSocket | `github.com/coder/websocket`（前 `nhooyr.io/websocket`） |
| 图片解码 / 缩放 / 重编码 | 标准库 `image/jpeg` + `golang.org/x/image/draw` |

标准库的 JPEG 编码器**不写 EXIF**，所以"服务端强制重编码即脱敏"（§2.2）是免费的，不需要额外的元数据处理。

国内网络下 Go 模块代理是必设项：`GOPROXY=https://goproxy.cn,direct`。

### 11.2 仓库布局

服务端和相册端在**同一个仓库**（D6）：

```
app/                      Android TV 相册（已有）
server/                   Go 服务（新）；独立 go.mod，Gradle 完全不碰它
  cmd/tupingd/main.go
  internal/api/           HTTP 端点、鉴权、限流
  internal/phash/         规范缩略图 → pHash‖dHash、黑边剥离、方差
  internal/store/         SQLite、迁移、检索
  internal/qr/            短码 → 二维码 PNG（含缓存）
  web/                    H5 评论页，go:embed 进同一个二进制
  Dockerfile              只 COPY 预编译二进制，FROM alpine
  README.md               服务端自己的部署文档
  go.mod
miniprogram/              WeChat 小程序（第二阶段）
tools/mock-review/        Node mock（照 tools/mock-nas 的样子）+ verify.js

```

这样选的三个理由：协议在早期天天改，一次提交能同时改协议文档、TV 端、服务端和 mock；仓库的房子规矩（自包含工具链、纯 ASCII 脚本、钉死依赖）不用重建第二套；协议文档只有一个真相源。代价是**两套版本号**——APK 的版本仍只写在 `app/build.gradle.kts`，服务端由 `-ldflags -X` 注入，两边**不要试图对齐**，tag 用 `app-v1.4.0` / `server-v0.1.0` 区分。

**什么时候该拆出去**（任一触发就拆）：

1. 有第一个人（不是作者）要自部署图评 —— 那时它需要自己的 README、compose、release 和 issue 区；
2. 服务端有了独立的版本节奏（要紧急修线上 bug，而 APK 还在测新功能）；
3. 要给图评单独的许可证或品牌。

拆分很便宜：`git subtree split -P server -b server-split` 连历史一起带走。所以"现在合、以后拆"是安全路径；反过来更麻烦。仓库**不要改名**：slug 硬编码在 `UpdateChecker.kt:287`、`release-manifest.ps1:37`、`publish-gitee.ps1:34` 三处，而且 GitHub 与 Gitee 是两个不同账号。

### 11.3 开发机不需要 Docker，也不需要 NAS

这一条让前四个里程碑都变简单：服务在 **Windows 上直接跑**（`go run ./cmd/tupingd`），监听 `0.0.0.0:8080`，手机连同一个 Wi-Fi 访问 `http://<开发机 IP>:8080/c/{code}` 就能测完整条链路——**§15 实验 1 今天就能做**。容器只用于最后把服务搬到 NAS 上长期运行。

### 11.4 工具链

按这个仓库的既定做法（`F:\android-toolchain`，自包含、不装系统级东西），Go 解压到 `F:\go-toolchain` 即可，和 Android 那套并列，删起来也是一步。

### 11.5 构建与部署

```powershell
# 在 Windows 上直接产出 Linux 二进制，NAS 上不需要 Go 工具链
$env:GOOS = 'linux'; $env:GOARCH = 'amd64'   # 本机 NAS 是 x86_64（§11.6）
go build -trimpath -ldflags '-s -w' -o dist/tupingd ./cmd/tupingd
```

镜像只做一件事：把二进制拷进 `alpine`（约 3 MB 的基础镜像，而不是 800 MB 的 SDK 镜像）。

```yaml
services:
  tuping:
    build: .                                       # 附件里有 Dockerfile，只拉一个 alpine（3 MB）
    restart: unless-stopped
    ports: ["8080:8080"]
    volumes:
      - /vol1/docker/tuping/data:/data
    environment:
      # TUPING_BASE_URL: "http://192.168.31.14:8080"   # 可选钉子；不填就用"谁在连"的地址（§17.20）
      # TUPING_SECRET: "<random>"                    # 可选，不填就由服务器生成并存到数据目录（§17.19）
      TUPING_ADMIN_TOKEN: "<random>"
      TUPING_DB: "/data/tuping.db"
      TUPING_THUMBS: "/data/thumbs"
      # TUPING_REGISTER_TOKEN: "<optional>"          # 设了以后，注册照片必须带令牌（办公室/宿舍这类不信任局域网时用）
```

- 部署者要填的只有一个值：`TUPING_ADMIN_TOKEN`。地址与签名密钥都有默认（§17.19、§17.20）。
- **真正决定二维码内容的是电视**（§17.6）。电视注册照片时会把自己访问服务端用的那个地址一并报上来，服务端把它记在那张照片的短码上，二维码、H5 页面里的图片、以及注册回包里的 URL 全部以它为准。
- `TUPING_BASE_URL` 从 §17.20 起是可选的钉子，用在"调用者上报的地址不能信"的场合（反向代理改写 Host、老客户端不上报地址）。填了它就必须是**手机能访问到的那个地址**——填成 `localhost`、容器名或一个公网访问不到的局域网地址，后果是二维码指向手机打不开的地址，而电视上的表现只是"扫了没反应"。
- 电视端填的是这台服务端的地址（`http://192.168.31.14:8080` 这种）。它和二维码里的地址来自同一个来源，不需要人肉同步。
- 电视端的明文 HTTP 不需要改 manifest：`network_security_config.xml` 的 base-config 已经是 `cleartextTrafficPermitted="true"`，理由正是"主机名由用户在运行时填"——这条同样适用于图评。
- 备份 = SQLite 的 `.backup` + `thumbs/` 目录 rsync 到 NAS 的另一块卷。
- 安全边界重申：**这个端口绝不映射到公网**（§10.1）。

**谁想部署，拿到的是什么。** 部署者不会自己编译 Go，所以发布形态是 release 附件，而不是"请先装 Go 工具链"：

| 附件 | 用途 |
| --- | --- |
| `tupingd-linux-amd64` / `tupingd-linux-arm64` | 预编译二进制，多架构（对应 §11.6 的答案） |
| `Dockerfile` | 三行：`FROM alpine` + `COPY` 二进制 + `ENTRYPOINT` |
| `docker-compose.yml` | 自己构建镜像的那一份：`build: .`，改 `TUPING_ADMIN_TOKEN` 一个值（地址与签名密钥都有默认，§17.19／§17.20） |
| `docker-compose.image.yml` | **一行部署**：`image:` 指向已发布的镜像，不需要构建、不需要二进制（§17.22） |
| `README.md`（服务端） | 部署说明 |

第一版不发容器镜像到 registry：国内拉 Docker Hub 和 ghcr.io 都不稳，而 `docker compose build` 只拉一个 3 MB 的 alpine，体验反而更好。等有外部用户了再正经发镜像。

> **§17.22 推翻了这条。** 2026-10-11 的第一次真实部署正是卡在 `FROM alpine:3.20`（镜像源回 401、直连被重置）—— 本地构建**同样依赖 registry**，所以"不发镜像"省下的不是网络，而是把认架构、下二进制、四个文件同层全推给了部署者。现在镜像发在 Docker Hub 上（多架构），部署是一份 compose。

**部署路径已确认**：飞牛的容器面板支持 `docker-compose.yml`（2026-10-09 实测），所以 compose 就是主部署路径，不需要退化成一堆手填的单容器表单。服务端 README 的第一步因此是 `uname -m` —— 它决定下 `amd64` 还是 `arm64` 那个二进制。

**面板这条路的两个前提（2026-10-11 补，§11.5 的补充而不是改结论）**：

1. 面板新建项目时选的目录就是 `docker compose` 的工作目录，也就是 `build: .` 的上下文。所以 `tupingd-linux-amd64` 和 `Dockerfile` 必须和 `docker-compose.yml` **同层**（Dockerfile 里是 `COPY tupingd-linux-amd64`，按文件名取），面板里那个「构建」按钮等价于 `docker compose build`，换了二进制不点它就会继续用旧镜像。发布目录因此多一个 `.dockerignore`：它挡掉 `data/`，免得每次构建都把库和缩略图打包给 Docker daemon。
2. **bind mount 的 `/data` 属主由服务器自己接管（这条在 2026-10-11 当天改过一次，见 §17.21）。** 宿主目录由 Docker 以 root 创建、权限 755，而服务进程是 uid 10001，于是 `tuping.db` 建不出来：容器起来几秒就退出、`restart: unless-stopped` 让它反复重启，日志里只有一行 `unable to open database file`。构建阶段那句 `chown -R tuping:tuping /data` 只作用于镜像层，对 bind mount 无效。最初的结论是"让部署者 SSH 上去 chown 一次"；§17.21 把它改成"镜像以 root 起步、二进制接管属主、然后立刻降为 10001"，因为要求每个部署者知道 uid 是什么，是把实现的细节写进了使用说明。

### 11.6 目标架构

**已确认（2026-10-09）：这台飞牛是 `x86_64`，所以本机构建用 `GOARCH=amd64`。**

`arm64` 的二进制照样一起发（§11.5 的附件表里两个都有）——别人的 NAS 可能是 ARM，而这正是"发布形态是预编译二进制"的意义所在：部署者不需要知道 Go 是什么，只需要知道自己该下哪一个。

## 12. 隐私与合规清单

图片域必付的代价，缓解手段是收敛面：

1. **不提供按哈希查询的接口**。查询一律走短码 + 上传缩略图（上传本身就是持有证明）。
2. 注册/查询一律限流（每设备、每 IP），防止批量探测"某张图有没有人评论过"。
3. 只对显式开启图评的相册/文件夹上传。
4. 缩略图：服务端强制重编码（去 EXIF/GPS）、签名 URL、TTL 30 天无访问即删、路径不可枚举。
5. 相册主人可一键删除"这张图 + 它的全部评论"，并可关闭该图的评论。
6. `openid` / `ip` 只存 HMAC；公开页面上只有昵称和评论内容。
7. 第二阶段补：隐私政策、用户协议、投诉/删除入口、内容留存与通知-删除机制。

## 15. 实验

实验脚本都写在 `%TEMP%\tuping-exp\`（不入库、随时可丢），素材落在 `artifacts/tmp/`（已 gitignore）。进文档的只有结论和步骤——所以换一个会话、换一台机器，这几页仍然能照着重跑。

### 15.1 已经量完的：pHash 敏感度（离线）

拿 `tools/mock-nas` 的素材在临时目录里跑的（脚本不在仓库里，只有结论进文档）。基线是同一张图按 3:4 裁剪、再等比缩到 320px 得到的"规范缩略图"；其他每一行都是同一张图经过一种变形后，与基线的 **pHash(64) ‖ dHash(64)** 的汉明距离。

| 变形 | 合计/128 | pHash/64 | dHash/64 | 方差 |
| --- | --- | --- | --- | --- |
| 重编码 JPEG q60 | 0 | 0 | 0 | 5857 |
| 重编码 JPEG q35 | 0 | 0 | 0 | 5842 |
| 亮度 +8% | 0 | 0 | 0 | 6804 |
| **补边到 16:9（服务端不处理）** | **43** | 17 | 26 | 3487 |
| 补边 → 服务端剥掉黑边 | **6** | 4 | 2 | 5902 |
| **裁剪到 16:9** | **54** | 25 | 29 | 5758 |
| 平移 5% 后重取（近重复） | 26 | 12 | 14 | 6158 |
| 另一张照片 | 54 | 22 | 32 | 4377 |
| 纯白图 | 44 | 15 | 29 | 0 |
| 浅灰图 #EEEEEE | 44 | 15 | 29 | 0 |
| 纯白 vs #F8F8F8（两张扁平图互相） | **0** | — | — | 0 |

三条结论，都已经写回 §3.3 的参数里：

1. **良性变形完全免费** —— q35 重压、亮度 +8% 的距离都是 **0**。整个"pHash 兜底"的方案成立。
2. **补边可以救，裁剪救不回来** —— 补边到 16:9 会让距离飙到 43（远超阈值），但服务端**先剥掉黑边**就能回到 6；而裁剪到 16:9 的 54 位和信息彻底丢失等价，等于把同一张照片认成另一张。**所以规范缩略图必须等比，服务端必须做黑边剥离。**
3. **扁平图不是"哈希随机"，而是"互相碰撞"** —— 纯白和 #F8F8F8 的距离是 **0**。两张肉眼几乎无差的白墙照会直接被合并成同一张。低方差护栏不是保险，是必需的。

顺带一条参数修正：阈值从 pHash ≤4 放宽到 **≤6**（且 dHash ≤6）。真匹配最坏是 4（剥黑边后的情形，正好贴着原阈值），而最近的真不同样本是 12 —— 6 落在中间。

### 15.2 还需要在真机上做的

**实验 1：微信能否打开局域网明文地址**（决定第一版的交互形态）

- 靶子：`http://192.168.31.192/` —— 302 到 `http://192.168.31.192:50316/`，200 OK，全程明文 HTTP、不涉及证书。用它而不是开发机，是为了避免 Windows 防火墙把入站连接挡掉，把变量搅在一起。
- 素材：`artifacts/tmp/tuping-experiment/`（已被 `.gitignore` 忽略）里四张 1920×1080 的画布，二维码在左下角 48px 处、白底留白 24px —— 和 §9.1 的设计几何一致。**必须用整张画布**而不是裸的二维码 PNG：任何图片浏览器都会缩放适配，裸图的"160px"到了电视上就不是 160px 了。
- 做法：电视上用图片浏览器全屏打开 `on-photo-200px.png`，手机微信扫一扫。
- 判据：能打开 → 第一版 H5 方案成立；被拦截或有警告 → 把原话记下来，第一版要改形态。

**实验 2：飞牛 `m` 档到底给什么 —— ✅ 已答（2026-10-09）**

起因是 `docs/fnos-photo-api.md` 里记的 `m` = 1920×1080 看着像按 16:9 裁的，而那条测量是在一张 16:9 的照片上做的，证明不了任何事。于是做了两个样本：

| 样本 | 上传的原件 | 取回来的 `m` | 画幅 | 与原件指纹距离 | 角落标记 |
| --- | --- | --- | --- | --- | --- |
| 1 | 1080×2400（短边 1080） | **1080×2400**（原样返回） | 一致 | **0** | 那张没有标记 |
| 2 | 3000×4000（短边 3000） | **1280×1707** | 一致 | **2 / 128**（pHash 2） | TL / TR / BL / BR 全在 |

**结论：`m` 保比例，不裁切也不补边；规则是"短边上限 1280，不放大小图"。**

- 样本 2 的实测 1280×1707 与"短边 1280"的**预测完全一致**；样本 1 的短边 1080 本来就在上限内，所以原样返回——两个样本合起来才把规则钉死。
- 我一度把常数写成 1080，那是从样本 1（**根本没发生缩放**）过度概括出来的。真值是 **1280**。
- 样本 2 才是真正有意义的那次：原件被降到 0.427×，指纹只动了 2 位，阈值 6 还剩 4 位余量。**§3 的整个假设第一次在"真的发生了缩放"的路径上得到验证。**
- 四个角标记在两个档位都完整 —— 裁切和补边被排除，而且是**看得见的**排除，不只是数字上的。（分析器在样本 2 上报出的 14px 纯色边是我画在测试图上的品红边框，灰度 105 就是品红，不是 padding。）

**顺带一条对 §3.5 很重要的**：`o` 档就是上传的原文件字节 —— 下载回来与本地原图的 **sha256 完全一致**（`7a6fcaf9…`，1 022 407 字节，逐像素最大差 0）。所以 TV 从 `o` 算出来的 sha256 就等于库里的原文件哈希，"同一份原文件被多个相册索引"这条路径在飞牛上是真的成立。

**设计动作**：规范缩略图直接用 `m`（它本来就在查看器的磁盘缓存里，见 §3.5），注册照片**不需要**为算哈希去下原图；原计划里"带宽预算重算"不用做了。

另有一条附带发现，已写回 §3.3：分析器按"纯色边"检测（列标准差 ≤2）时，把样本 1 那张照片**本来就有的浅色边**（均值 243，左 33 / 上 16 / 右 24 px）当成了 padding 剥掉，反而把距离从 0 推到 **17** —— 超过阈值。所以黑边剥离必须限定在近黑/近白且对称的边上，并且当作"追加候选"而不是替换。

**实验 3：微信原图三段哈希**（要两部手机）—— A 发原图 → B 保存，比对 sha256；B 再发给 C，再比一次。把"字节不保真"这个前提钉死在自己的环境里，而不是相信文章。

**实验 4：电视上二维码的可扫性** —— 用同一批画布，160 / 200 / 240 px 三档，在 2 米 / 3 米 / 4 米分别扫；`on-black-200px.png` 是同尺寸但背景纯黑的对照，用来分开"码太小"和"背景照片干扰"这两个原因。

**实验 5：飞牛 NAS 的 CPU 架构 —— ✅ 已答** —— `x86_64`，所以 `GOARCH=amd64`（§11.6）。`arm64` 的构建仍然要发。

### 15.3 结果怎样改设计

| 实验 | 结果 | 改哪里 |
| --- | --- | --- |
| 1 | 打不开明文内网地址 | 第一版改用 NAS 自己的 HTTPS（微信会警告自签证书），或 H5 退化成"用手机浏览器打开"，或提前上公网 HTTPS |
| 2 | **已答：等比保比例**（§15.2） | 规范缩略图直接用 `m`；注册不需要下原图，带宽预算的风险消失。附带的"剥边会误伤"已写回 §3.3 |
| 3 | 三段哈希全不同 | 确认 sha256 只能覆盖"同一份原文件"，分层方案按原样走 |

| 5 | **已答：`x86_64`** | 本机交叉编译用 `GOARCH=amd64`；`arm64` 照样发，别人的 NAS 可能是 ARM |

## 17. 实现注记（2026-10-09）

这一节只记**实现与上面正文不同**的地方，以及实现过程中被测试抓出来的东西。正文没有被改写的部分就是
实现的样子；下面每一条都对应代码里的一处注释。

### 17.1 比 §5 多出来的东西

| 多出来的 | 为什么 |
| --- | --- |
| `devices` 表（id / token_hash / owner_token_hash / name / 时间） | §7 说设备令牌"申请"得到，那就得有个地方发。设备 id 第一次由服务端生成，之后相册端一直用它 —— 相册端自己造 id 的话，同一台电视重装一次就会变成两个设备 |
| `device_local` 表（device_id / source / local_id → image_id） | §6.2 的"同一设备重复注册同一张照片"要答得出来。local id 是相册端的命名空间，塞进 `photos` 会把两张表的寿命绑在一起 |
| `photos.stripped_width` / `stripped_height`、`phash_stripped` | §3.3 说剥边后的指纹是**追加候选**。它同时是一个**不同的画幅**，而画幅正是候选集的过滤器；用补过边的画幅去比，正好会把这一条要救的情况挡在门外（见 17.3） |

### 17.2 §3.2 的两处读法

- **sha256 命中时也跟随 `merged_into`。** 命中一行已被合并的照片时，返回的是它所在组的根，`matched`
  仍然是 `sha256`。两种理解都说得通（"命中后再跟随"或"命中即返回"），但一张照片只能有一个 `image_id`，
  而 `merged_into` 是那个身份的唯一记录 —— 于是跟随指针是唯一自洽的读法。
- **"疑似"不落库。** §3.2 说 pHash 7–11 时"记一条疑似关系，等带 sha256 的一方来认领"。实现里这个
  区间被**算出来并报告**（`RegisterResult.Suspects`），但不写表：认领本来就不需要那条记录 ——
  带 sha256 的一方来了，`photos.sha256` 命中就直接认领。等真有第二个人需要读这份疑似列表时再加表，
  比先加一张没人读的表便宜。

### 17.3 两处只有测试能发现的 bug

1. **日志中间件把 `http.Hijacker` 挡住了。** 记录状态码的那层 `ResponseWriter` 包装只实现了
   `WriteHeader`，于是 `WebSocket` 升级在 `coder/websocket` 里走到"这个 writer 不支持 hijack"，
   回了 **501**。电视上的表现只会是"弹幕永远不来"。现在包装转发 `Hijack` / `Flush` 并实现
   `Unwrap`，`api` 的端到端测试真的连一次 WebSocket 并断言收到那条评论。
2. **剥边之后的画幅。** 剥掉 padding 之后，指纹是按**剥完的图**算的，但画幅过滤器最初拿的是**补过边
   的图**的比例 —— 于是一张被聊天软件补过边的照片永远进不了候选集，而那正是整个 pHash 兜底存在的
   理由。现在每个候选指纹各带自己的宽高。

### 17.4 EXIF 方向

服务端在算指纹**之前**按 EXIF Orientation 把像素扭正。方向搞反不会看起来像 bug，只会看起来像"这张
照片转了 90 度"—— 6 和 8 的第一版就是这么错的，而所有按**尺寸**检查的断言都照样通过（两者都交换
长短边）。现在这一条是按像素对着一个独立写出来的正向变换断言的（`TestApplyOrientation`）。

### 17.5 环境变量（§11.5 之外）

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `TUPING_OPEN_REGISTRATION` | `true` | `false` = 只有已持有令牌的设备能注册新设备 |
| `TUPING_REVIEW_WORDS` / `TUPING_REJECT_WORDS` | 空 | 逗号分隔，命中分别进待审 / 直接拒（§8 的分级词表） |
| `TUPING_ADDR` | `:8080` | 监听地址 |
| `TUPING_THUMB_TTL` | `720h` | 与 §12.4 的 30 天一致，但可以调 |
| `TUPING_SECRET` | 空 = 自动 | 签名密钥。空时由服务器生成并存到文件（§17.19） |
| `TUPING_SECRET_FILE` | 数据库同目录的 `secret` | 上面那个文件的位置 |

`tupingd -check` 把当前配置打印出来，用来核对容器里的环境变量是不是真的传进去了：`baseUrl` / `db` / `thumbs`
是实际取值，`adminToken` / `registerToken` 只显示"已设置/未设置"（§11.5 的密钥不打印原文），`secret` 说明它打算
从哪儿拿（`TUPING_SECRET` / 文件 / 第一次启动时生成）。它不创建任何文件，所以在还没启动过的 NAS 上也能跑 ——
这是"填错一个地址，二维码指向手机打不开的地址"那条风险唯一能自查的地方。

### 17.6 二维码里的地址由电视决定，不由服务端猜（改 §11.5 的结论）

§11.5 原来要求部署者把 `TUPING_BASE_URL` 填成"手机能访问到的地址"，并把它当作二维码内容的唯一来源。
实践下来这条不成立：**服务端不知道电视是从哪个地址找过来的。** 同一份服务端可以同时被局域网地址、
公网端口映射、内网穿透域名访问，哪一个能用只有发起连接的那一端知道。实测踩到的具体形态是：电视上
填了 `106.52.237.179:53347`（内网穿透），`docker-compose.yml` 里还是出厂示例的 `192.168.31.14:8080`，
于是电视一切正常（连接、上传、弹幕都通），而**每一位客人扫到的都是一个打不开的局域网地址**——症状
完全不在电视上，只有客人手机能看见。

改成：注册照片时，电视把自己配置的图评地址（也就是它刚刚用来上传的那个地址，`ReviewClient` 里的
`base`）放在 `meta.baseUrl` 里一并报上来，服务端校验后记在**短码**上（`codes.base_url`，因为短码才是
二维码指向的东西、而且可能被多台设备共享）。之后：

| 用途 | 取值 |
| --- | --- |
| 二维码内容 | 短码记录的地址 |
| `/c/{code}` 页面里的缩略图 `src` | 同上 |
| 注册回包 / 详情接口的 `qrUrl`、`thumbUrl` | 同上 |
| 以上任一处的兜底 | `TUPING_BASE_URL`（§17.20 起改为"钉住的值，否则是这次请求用的地址"） |

三条约束：

1. **不是信任 Host 头。** §11.5 拒绝 Host 头是对的——那是任何人随便填的。这里的地址来自一台**已经
   持有设备令牌**的客户端，它只是说出自己刚才成功连上的地址。仍然校验：只接受 `http`/`https`、必须有
   host、丢弃 path/query、拒绝带用户名密码的 URL、限长 200；不合法就退回 `TUPING_BASE_URL`。
2. **已有短码不改指向。** 同一个短码可能已经印出去、截过图、发在群里了，重新注册时换了网络不能让它
   悄悄改指向。要整体换地址，删掉重新注册。
3. **服务端仍然警告。** `TUPING_BASE_URL` 是私有地址时，启动日志和 `/healthz` 都会说出来——因为那
   仍然是"电视没上报地址"时的兜底，兜到一个手机打不开的地址依然是错的。（§17.20 把这个兜底从"配置里必须有
   一个"改成"调用者自己说"，警告因此只在真的钉了值时才出现。）

`/v1/qr/{code}` 现在还会返回 `X-Page-Url` 响应头，写明这张二维码里到底编的是哪个地址。二维码是一张
地址的图片，在没有摄像头的机器上本来是读不出来的：
`curl -sD - -o /dev/null http://<host>:8080/v1/qr/<code>` 一眼就能看到答案。

### 17.7 设备令牌被拒，是电视上唯一一个"没法自救"的状态（2026-10-10）

**在电视上原样读到的症状**：设置页 `图评连接状态` 是绿色的 **已连接 http://…**，而查看器右下角的
**图评** 按钮是灰的——遥控器左右走的时候直接跳过它，**图评菜单（二维码 / 弹幕 / 弹幕数量）打不开**，
画面上也没有二维码。这个组合读不通："服务器已连接"和"功能整层不可用"同时为真。

**成因是两个问题共用了一个词。** "已连接"来自 `/healthz`，而 `/healthz` **不需要鉴权**；注册照片
（`POST /v1/photos`）、读评论、订阅弹幕**都要设备令牌**（`requireDevice`，§7）。电视上存的令牌来自
另一个服务端时——服务端重装过、数据库被重建、从旧备份恢复、或者电视上的地址被改到另一台——`/healthz`
照样 200，而所有带令牌的请求都是 401 `unauthorized / 设备令牌不对`。客户端把它记成
`ReviewStatus.Failed`，查看器按"没有服务器可说话"把按钮置灰，于是**一台能连上的服务器把图评整层锁死**。

第一次复现的原始证据（Android TV 模拟器 + 一个空库的 `tupingd`，电视上留着前一天那台的令牌）：

```
I/ReviewRepository: 图评: checking status (mode=slideshow, url=10.0.2.2:8080)
I/ReviewRepository: 图评: http://10.0.2.2:8080/ answered ...        ← 设置页那一行读的就是这句
I/ReviewRepository: 图评: Api(code=unauthorized, message=设备令牌不对) ← 注册照片的失败
```
```
GET  /healthz    200
POST /v1/photos  401
```

**为什么会永远好不了**：`ensureDevice()` 只要看到令牌非空就认为这台设备已就绪；`forgetDevice()`（它自己
的注释就写着"改地址之后用"）**一个调用点都没有**；而设置页每次刷新都会用一次成功的 `/healthz` 把
`Failed` 覆盖回 `Online`——所以连失败原因都不会留在屏幕上，用户连"该去清应用数据"这条线索都拿不到。

**三条改动：**

1. **被拒就重新注册。** 任何带令牌的调用（注册照片、读评论）拿到 `unauthorized`，就丢掉 device id 与
   令牌，按一台**新设备**重新申领，再把那次调用重跑一遍。为什么必须换 id：`handleDeviceRegister` 对
   **已存在**的 id 会先验旧令牌，验不过直接 401 `设备令牌不对`，所以服务端唯一保证接受的身份是一个新
   身份。代价是它的 devices 表多一行（这个应用不删图，旧 owner token 丢掉没有别的后果）。
   **只有 401 才修**：把丢包也当成"被拒"，会为了一个不需要新身份的失败往服务端堆幽灵设备。修复用一把
   锁串行化——打开一张照片会同时注册它自己和后面四张，两次并发修复会各发一个设备，谁输谁手里就是一个
   服务端已经换掉的令牌。
2. **"已连接"必须同时意味着"这台设备被接受"。** 健康检查之后再补一次**带令牌的探针**：
   `GET /v1/comments`（**故意不带 imageId**）——`requireDevice` 在参数校验之前跑，所以答案干净地分成两半：
   401 是"这个令牌不是我的"，**400「缺少 imageId」是"令牌通过了"**（非 401 的任何状态都算通过）。
   不拿一个不存在的 imageId 去问，是因为那会把问题从"凭证"变成"照片在不在"：mock 对不存在的照片答
   404，而 `tupingd` 答 **500**（`store: not found` → `服务器出错了`，见下面的已知问题）。探针被拒 →
   先按第 1 条修一次；拿着新身份还被拒（`TUPING_OPEN_REGISTRATION=false` 这类）→ 把服务端原话写在那一行
   上。探针**答不出来**（网络问题）**不算被拒**：健康检查刚刚证明服务器在，没必要为一次丢包换掉身份。
   修复只有一条路径（`withDeviceRetry`）：第一次在真服务端上跑的时候，探针和照片注册各自修了一次，服务端
   日志里出现两行 `device issued`，电视最后拿着的是输的那一个令牌——所以两条路径共用同一把锁。
3. **一次调用失败不再锁死图评菜单。** 按钮只在 `NoServer`（没有可用地址）时置灰。失败态下按 OK 照样
   打开菜单，并在屏幕底部把原因念一遍：开关只能决定"画什么"，不能让服务器回话，但它同时是用户关掉这一层
   的唯一入口，而电视上没有控制台。

顺带修掉一处一直没生效的读取：`report()` 用 `error.cause as? ReviewError` 去取服务端原话，而
`ReviewError` 是值、不是 `Throwable`，`cause` 永远是 null——所以状态行一直显示
`Api(code=unauthorized, message=设备令牌不对)` 这种 Java 味儿的字符串，而不是服务端写的"设备令牌不对"。
现在从 `ReviewException.error` 取（`reviewErrorOf`），并且有单测盯着这条判定。

**已知问题（本次没改）**：`GET /v1/comments?imageId=<服务端不持有的照片>` 在 `tupingd` 上答 **500
`服务器出错了`**（日志里是 `server error err="store: not found"`），mock 答 404。两端不一致，而且 500
无论如何都不是"这张图没有评论"的正确说法。它会以两种方式露出来：探针如果去问一张不存在的图（所以现在
不问），以及一张照片在服务端被删/被保留策略清掉之后，电视再去读它的评论。客户端不受它影响（`/healthz`
之外还有探针，页面照旧渲染），但要改的话是一条服务端改动 + 一次重新部署，所以单独拿出来说，而不是塞进
这次客户端修复里。

### 17.8 弹幕在真机上第一次被看见（2026-10-10）

一条真评论："这是在干什么呢"，发出去之后电视上出现的是 **`这是…`**。四个问题，按现场报的顺序：截断、
字号偏大、速度偏快、以及"同一个弹幕间隔不能小于 5 秒"。**第一条是 bug，而且它解释了字号那一半。**

**先把范围切开**：直接问服务端，存下来的是完整的一句 ——

```
{"items":[{"id":"01M4K74M…","content":"这是在干什么呢","status":1,…}]}
```

所以截断在电视端的渲染里。

**根因是单位**：`DanmakuFeed` 拿 `level.textPx`（38）当**像素**算一行的宽度（`ReviewComment.widthPx`：
CJK 一字一 em），而 `DanmakuOverlay` 用 `level.textPx.sp` 去**画**。在 320dpi 的电视上 `38.sp` = **76 像素**，
于是"给这行留的框"只有实际字宽的一半——`Modifier.width(宽/密度)` 把文字截到两个字加省略号；同时字号也
正好是设计值的两倍，这就是"字体有点大"。一句话：**数字本身没错，单位错了，两个症状是同一个错。**

**改法**：

1. **按像素画**：`fontSize = with(density) { level.textPx.toSp() }`。这样 `textPx` 就是真机像素，和这层的
   其它数字（速度、行高、45% 上限、band）终于同一套坐标。
2. **宽度改成量出来的**，不再是估的：§9.5 一直写着"文字宽度用 `TextMeasurer` 量一次并缓存"，但代码里
   是 `ReviewComment.widthPx` 的估算（CJK 1em、拉丁 0.55em）。估算对中文够准，对 `WWWW` 这种宽字母不
   够——"框比文字窄"这一类 bug 会以同样的方式再来一次。现在 overlay 用 `rememberTextMeasurer()` 量好，
   经 `DanmakuFeed.offer(comment, now, widthPx)` 传进去（这个参数有默认值，纯逻辑的测试不受影响）。
3. **数字**：速度 320 → **260 px/s**（横穿 7.4 秒），字号 **34 / 40**（原本 38 / 44）。代价写在 §9.5：
   3 秒间隔 + 6 秒上限已经装不下最长的一条（10.7 秒），那种组合下照片照常前进。
4. **循环 + 5 秒下限**：进图时照旧错峰播最近几条，之后**不停地轮转**这张图的评论（每 1.2 秒轮到下一
   条）。下限在 `DanmakuFeed.REPEAT_COOLDOWN_MS = 5_000`：同一条从**上一次进入屏幕**算起 5 秒内不再
   出现，换图清零。为什么这个下限是必要的：一张只停留几秒的照片靠"轨道没空"就够，但循环之后，一条刚
   走完的弹幕会被下一轮立刻再推上来；而"评论列表变化"本来就会重跑开场重播，那条规则以前连
   "刚刚走完又立刻重来"都挡不住。

**循环顺手暴露的第二个 bug**：帧时钟在没有线在动时会 `break`（这条规矩是为了别让一块电视盒子空转 60Hz），
而循环推一条弹幕**不改变任何可观察状态**——于是如果那一刻层是静止的，新推上来的这条会停在右边缘永远不
动，还把那根轨道永久占住。现在 offer 成功会 bump 一个 `lineTick`，帧时钟以它为 key 重新起跑。

**装上之后第一个晚上就撞到的第三个（1.4.4）**：给第一张图发了弹幕，**翻到下一页，那条弹幕也飘过去了**；
而直接打开第二张图不会，符合预期。这一条正好说明"翻页"和"打开"的区别：

- 翻页那一帧 `currentId` 就变了，而图评的状态是**一个 effect 之后**才发布的（`openReviewedPhoto` 在
  `LaunchedEffect` 里跑）。中间那一帧，屏幕上摆的是"新图的 key + 上一张图的 identity"。
- 弹幕层的开场重播以 `(photoKey, comments)` 为 key，于是在这个窗口里被重启，立刻把**上一张图的**评论推
  了上去；而一条已经推出的弹幕会横穿 **7.4 秒**——所以这一帧的错误能被人眼看见。二维码在同一个窗口里
  也是错的，只是它只错一帧，看不见而已（而那是"码指向客人已经离开的那张照片"，性质更糟）。
- 直接打开第二张图没有这个窗口（状态从来没被设成第一张图的），所以看不到——和报告里说的一模一样。

**修法**：给 `reviewReady` 加一道身份闸门 —— 答案的 `identity.localId` 必须等于"屏幕上这张照片应有
的那个"，不相等就当作**没有答案**：层不参与组合，它连同正在横穿的线一起被销毁，新图自己的答案下一帧到
达、从空屏开始。这一条本来就是这层的规矩（"换图清空"），只是它此前看不见自己有没有被违反。

### 17.9 幻灯片卡在第四张：等待没有上限 + 预取被自己按住（2026-10-10）

**现场**：幻灯片放了三张正常，第四张就停住；**这次按右键也没反应**；退出播放之后手动右键立刻能翻；用户
的判读是"后面的图片没加载完成"，并顺带观察到"播放时后面的图片也不会自动加载"。

**这是同一件事的两半，而且第二半正好能解释第一半为什么越演越糟。**

1. **一步的等待没有上限。** 设计里"翻页绝不清空屏幕"是对的：下一张没解码完就把上一张留在屏幕上。但
   它只给了"等"，没给"等到什么时候"——真正的上限是媒体客户端自己的 `readTimeout(60s)`。于是碰到一张
   原图拉不动，幻灯片看起来就是**冻住**（而不是慢）。而 `预览原图` 的默认值 `仅用于幻灯片播放` 让这件事
   只发生在播放时：手动浏览看的是**缩略图**（网格早就缓存过），所以"退出播放就能翻页"这条线索正是这里
   漏出来的。
2. **预取窗口被这一步按住了。** `PrefetchAhead` 的 stand-down 条件包含 `pending.isNotEmpty()`，本意是
   "有一张我们自己在等的图时，先别去热别人"。可是**播放中队列里那一步就是下一张图**：窗口从这一步排队
   开始就被按住，按到它加载完为止——如果它很慢，窗口就被按很久，**后面那张同样是冷的**，一张慢图于是
   变成"整场都不再加载"（用户看到的那句）。手动翻页时这个规则是对的（人在等眼前这张），播放时它是反的。

**改法**（**其中"窗口不再为播放中的步骤 stand down"这一条已被 §17.13 推翻**：让位本身是对的，错的是让位的
方式——整段停掉而不是收窄——以及重锚的时机）：

- 预取窗口不再为**播放中的**队列步骤 stand down（手动翻页、以及"正在加载屏幕上的图/原图请求"仍然
  stand down）。播放正是最需要提前热后面几张的时候。
- 一步的等待有了上限：**8 秒**（`STEP_PATIENCE_MS`，等于默认间隔，超过就已经看得出是停了）——**这条已改成
  跟随间隔的 4–12 秒，且到点不再取消在途下载，见 §17.13**。到点还没
  等到原图就**改用缩略图档**把它显示出来——缩略图网格里通常已经在盘上——并在屏幕底部说一句
  `这张原图还没到，先看缩略图`。照片出现在屏幕上、演出保住节奏，原因也留在屏幕上，和 §17.7 那句"电视上
  没有控制台"是同一个道理。这个降级只作用于**这一步**，落地即清（`downgraded`），下次再看这张图仍然按
  原图请求。

**顺手发现、这次没改**：查看器里的 `onDanmaku`（"有新评论时把这张多停一会儿"的实现）**没有任何调用
点**——`DanmakuOverlay` 不接受回调，所以设置页那一行 `有新评论时多停一会儿` 目前是空的。要接上它，正确
的位置是"一条**新**评论到达"（socket / 历史合并）而不是"一条弹幕被画出来"，否则 §17.8 的循环会不停给
这张图续命。它和这次的卡顿无关（正因为它是死的，才没有变成"每张图都被续 6 秒"）。

### 17.10 弹幕全挤在第 0 行，以及第三轮速度（2026-10-10）

**现场**："弹幕有点快，再慢一点，弹幕分 3、4 行错开，现在是一行，文字重叠了。"

**轨道那条是 bug，而且是我 §17.8 加的循环把它放大的。**（**这条规则本身又被 §17.14 换掉了**：现在是按行
轮流，行数由 少/多 设置决定。这里留着它，是因为"只挑最低可用行"与"空行优先"是这件事的两个反面，两个
都踩过。）`freeTrack` 只有一趟循环，遇到的**第一个**
"可用"轨道就返回，而"可用"有两种：**空着**，或者**上一根的尾巴已经让开入口**。于是第一条弹幕上了第 0
轨；1.2 秒之后（开场重播与循环的节拍）它已经让开入口，第 0 轨就又被判为可用——一趟循环先撞上它，
**后面每一条都继续上第 0 轨**。六根轨道、一行文字，几条弹幕紧挨着排队往下走，看上去就是"一行、文字挤在
一起"。修法是把顺序反过来：**先找空轨道，全占满了才轮到最后那条复用规则**。测试
`lines spread down the band before any track is reused` 把这条钉住：按节拍发 4 条，轨道必须是 0、1、2、3。

**顺带修掉的画法错位。** `DanmakuLine` 画的时候用了 `.offset(x = widthDp)`，而 `DanmakuFeed` 的几何
（`leftX`、`finished`、轨道间距、`StayExtension` 的横穿时间）都把 `leftX` 当作**左边缘**。两者差一个
字宽，后果是**一条弹幕没走完就整条消失**（`finished` 判定右边缘出屏时，实际右边还有整整一个字宽在屏幕
上），而轨道复用的判据也比像素落后一个字宽。现在没有这个偏移：`leftX == screenWidth` 时文字本来就完全
在屏幕外，模型和像素终于同一套坐标。

**速度**：260 → **220 px/s**（横穿 8.7 秒，最长一条 12.7 秒）。这是第三轮了（320 → 260 → 220），所以
把它写进 §9.5 的表里，连同轨道选择规则和它对幻灯片间隔的影响。

### 17.11 H5 那一页：昵称、表单顺序、举报（2026-10-11）

现场三条："我普通扫描，加评论，为什么显示 微信用户评论"、"评论信息放到表单下面吧，这样方便表单填写"、
"下面的举报按钮去掉吧"。

**昵称。** 页面本来就有输入框（`昵称（可留空）`）；**留空**时服务端用它自己的兜底值
`guard.DefaultNickname`，而那个值是 **"微信用户"**。这一页既没有登录、也没有任何微信的东西（§7 里"微信
身份"是第二阶段小程序的事），所以那句话是在替客人声明一个他从没用过的账号——难怪会被问"为什么"。现在
兜底值是 **"匿名"**，输入框的标签也写明"可留空，默认匿名"。

**同时把"记住昵称"真正做到。** §10.1 一直写着"填过的记在 `localStorage` 里下次预填"，但这一页**一行
JavaScript 都没有**（那是这一页最重要的性质之一），所以那条从来没实现过：提交成功后 303 回到同一页，
昵称框又空了，于是每一个回来的客人都在用兜底值。现在服务端把它记在 **`tuping_name` cookie** 里（提交
成功时写入，GET 时预填）。值是 `url.QueryEscape` 过的——昵称基本都是中文，而 cookie 值按 RFC 6265 只能
是 ASCII，`net/http` 对编码不了的值的处理是**悄悄不发这个 cookie**，不是报错。

**表单顺序。** 原来是"缩略图 → 一长串别人的评论 → 输入框"：一个人举着手机站在电视前，要打的字被推到
了屏幕外面。现在是"缩略图 → **昵称 + 输入框 + 提交** → 评论列表"，§10.1 的那一行顺序同步改了。评论列表
和空状态移到表单下面，改用它上面那条分隔线（原来那条线在表单顶上）。

**举报。** 页面不再有那一行链接。**接口保留**：`POST /v1/comments/{id}/report`、`GET /c/{code}/report/{id}`
和"第三次举报转 `status=0`"都照旧，§14 的契约测试一字未改——改的只是页面上那个入口，所以现在要举报得
直接开 `/c/{code}/report/{id}`。mock 的页面同步改了（它是参考实现，两边必须长得一样），而
`tools/mock-review/verify.js` 里那条"每条评论都提供举报链接"的断言**反过来**了：现在断言页面里**没有**
这个链接，免得哪天又被顺手加回来。

### 17.12 图评地址尾部的一个 NUL：一切"正常"，什么都没有（2026-10-11）

**现场**：本地 `tupingd` 起来了，穿透地址从主机和**模拟器内部**都连得通（`toybox nc` 连上），电视上
「图评」按钮却是灰的，二维码和弹幕都没有。

**根因不在链路，在电视里存的那个字符串。** prefs 里是：

```xml
<string name="server_url">106.52.237.179:53347&#0;</string>
```

尾部一个 **NUL**。`ReviewClient.normalize` 只做 `raw.trim()`——Kotlin 的 `trim()` 去的是空白，而 NUL 不是
空白——于是 `http://106.52.237.179:53347\0` 交给 `HttpUrl` 被拒，`configured = false`，
`ReviewStatus.NoServer`，**整层关闭**。日志是这句话：

```
图评: address 106.52.237.179:53347�� was rejected as unusable (blank, or not a URL)
```

而设置页把这些字符原样画出来，看上去完全正常——所以这句话读起来像在说一个既不为空、也没写错的地址。
NAS 地址行从 1.3.2 起就会折叠中文输入法的全角标点（`foldFullWidth`），**图评这一行什么都没折**。

**改法**：新增 `cleanServerAddress()`——去掉 C0/C1 与 DEL、零宽字符和 BOM，复用 `foldFullWidth` 折叠全角
标点与数字，再 trim。关键是**读和写两头都过**：读时清洗意味着电视上已经存坏的那个值**自己就好了**，
不需要有人在遥控器上重打一遍 17 个字符。`normalize()` 里再清洗一次，作为上链路前的最后一道。顺带一个
副作用是好的：`ReviewSettingsStore.fingerprint()` 用 NUL 作分隔符，现在地址里不可能再有 NUL，字段也就
伪造不出第三个。

**测试**：`ReviewAddressTest` 10 条——NUL、粘贴带进来的空白与换行、零宽与 BOM、全角数字与标点、https
保留、结尾斜杠、空值、以及"清洗不等于纵容"（端口 99999 仍然拒绝）。

**设备上验证**：日志变成 `checking status (mode=slideshow, url=106.52.237.179:53347)` →
`http://106.52.237.179:53347/ answered and accepts this device`，服务端签发 `device_id`；库里 49 张照片 /
49 个短码，`base_url` 正是电视上报的那个公网地址（§17.6）；电视缓存了 46 张二维码 PNG，二维码正常显示。

### 17.13 幻灯片里的原图：被取消的下载、锚点、以及一次 OOM（2026-10-11）

**现场**："幻灯片播放时，超过 3 页，就拉取不到原图了"，随后是"自动翻页，但都是原图找不到，加载的是
缩略图"。

**先量清楚**（真实 NAS、他人分享相册、原图 11.7 MB、冷缓存）：间隔 **8 秒**时屏上是**缩略图**（无障碍树
里读到的角标），间隔 **30 秒**时是**原图**。原图其实一直在下——Coil 磁盘缓存里持续落地 11–15 MB 的文件
——只是**永远赶不上**。三个原因，一个比一个隐蔽：

1. **忍耐上限到点会取消自己。** 到 8 秒就把**正在下载的那一层**改指缩略图，等于取消请求；已经读到的字节
   全部丢弃（只有完整读完的响应才进磁盘缓存），下一步从零再来。
2. **窗口恢复时从"当前这张"重新起算。** 预取窗口在每一步期间整段停掉，恢复后从当前位置开始热，于是它
   一直在给"已经当缩略图显示的那张"回暖，永远不领先。
3. **幻灯片默认随机。** 下一张不在"从当前位置往前数"的路上，位置窗口只能靠运气对上。

**还有一次崩溃**：约 7 分钟的 8 秒放映把 Java 堆顶到 192 MB，`OutOfMemoryError` 落在 OkHttp 的 reader
线程上（`okio…Segment.<init>` ← `Http2Reader.nextFrame`），应用被杀。稳定态 PSS 从 132 MB 涨到 296 MB，
Native（位图像素）从 42 MB 涨到 115 MB 且不回。

**改法**：

- **忍耐上限跟随间隔**：`slideshowSeconds` 夹在 **4–12 秒**（3 秒的放映不该闪缩略图，30 秒的放映也不该把
  画面停在上一张）。
- **到点不丢原图**：缩略图铺在**可见层**上，正在下载的那层继续跑；原图一到，走现成的"原图请求"路径把
  它原地换上去（`advanceOnThumbnail` + `originalRequest`）。慢的原图于是只值一瞬间的软，而不是整张丢掉。
- **窗口收窄而不是停掉**：等自己的图时只留**一路**下载（`ImagePrefetcher.prefetch(held=…)` 在批次之间读
  让位状态），其余照跑；**重锚只在层级或放映开关变化时发生**，而不是每次锚点移动。
- **放映时窗口覆盖整份列表**（上限 120 张）：它画的是一份随机表，位置窗口对它没有意义。
- **并发**：热原图 3 路（一般情况 4 路），让位时 1 路。

**§17.9 被本节推翻一处**：那里写着"预取窗口不再为播放中的步骤 stand down"。让位本身是对的（屏幕上的那张
必须先到），错的是让位的**方式**（停掉 → 收窄）和**锚点**（跟随当前位置 → 只在层级变化时重锚）。

**验证**：同一场景（8 秒、随机、冷缓存）连续约 20 张采样**全部是原图**；内存 Native 50→62 MB 到顶回落
（改前 42→115 MB 单调上涨）、Java 14–35 MB（改前 13→107 MB）、PSS 137→169 MB（改前 132→296 MB），
4 分钟以上无崩溃（改前约 7 分钟被杀）。

### 17.14 弹幕的行数、它们占多少屏幕，以及评论能打多长（2026-10-11）

**现场**，按出现的顺序："5 个评论就会用 5 行" → "图评少的时候就显示 2 行，多的时候就显示 4 行，每行会有
多个评论，但是不能挨得太紧，不能重叠" → "这两行站的区域太高了，你一行多高" → "2 行最多在顶部占全屏 1/4
的高度，4 行的话最多占全屏 2/5 的高度" → "评论最大字符 80 是不是太多了，在电视上显示太长"。

**行数由设置决定，不由评论条数决定**：`少` 最多 **2 行**，`多` 最多 **4 行**（`DanmakuLevel.tracks`）。
这是**上限**不是目标：只有一条评论时就只画一行。之前的两版都不对：6/12 根轨道配"一条评论一根"让 5 条评论
占 5 行；后来按评论条数分档（≤3→2 行、4–5→3 行、≥6→4 行）又在一个只有 3 条评论的真实照片上给出 3 行，
屏幕看起来和改之前一模一样——那条反馈就是"还是没有任何变化"。

**一行承载多条，靠轮流**：上一条进过哪一行，下一条就从**下一行**起试，一行里后一条要等前一条的尾部让开
**200px（≈0.9 秒）**。两种错法都留着记录：只挑最低可用行 → 全压在第 0 行（§17.10）；空行优先 → 一条评论
一行。轮流的 2 行放 3 条评论是 `0,1,0`，也就是"2 行、每行多条"。

**高度预算按整屏算**：从顶部安全区 96px 起，到**屏高的 1/4（少）或 2/5（多）**为止；行在这段区间里均分，
文字在**行内垂直居中**。旧实现是固定区间（96–700）加固定四分之一行距，两行会落在 226/528——"占了屏幕的
一半高度"。实测（1080p）：少 = y **118 / 205**（末行文字底 247.5 ≤ 270）；多 = y **113 / 197 / 281 / 365**
（底 415 ≤ 432）。

**评论长度上限 80 字 → 20 字**（§8）。算术：一行最多占屏宽 45%（= 864px，这个上限是为了把最长一条的横穿
时间压在照片的停留时间里），字号 34/40，所以一行约 **25 / 21 个汉字**——80 字里有五六十个字**永远只会变成
省略号**，等于手机在邀请人打一段电视上读不到的话。20 字在最大字号下是 800px，给宽字形（emoji 宽过一个
汉字）留了余量。库里已有的长评论不受影响，照旧被 45% 上限截断。

Go 的测试立刻抓到一个连带后果：广告模板用例 `看这里 http://spam.example.com` 是 **27 字**，会先被长度
拦下，那条测试于是不再测 URL 过滤。现在它压进 20 字，并且**断言每个用例都在长度上限内**——以后再改上限，
不会静默退化成"在测长度"。

**测试**：`DanmakuFeedTest` 20 条（行数上限、轮流、行距与预算、一条评论一行 vs 每行多条、间距恒等），
`StayExtensionTest` 8 条（新增"20 字在最大字号下不会被 45% 上限截断"）。

### 17.15 管理员登录：一个令牌、一个签名 cookie，以及页面上的编辑／删除（2026-10-11）

**要的东西**：图评那一页给管理员一个入口——访客照旧只能发评论，管理员可以编辑或删除。

**先划边界。** §7 早就把"管理员令牌"列为一种身份，但唯一的门是 `X-Admin-Token` 头或 `?token=`，也就是
curl。网页上的登录**不是新一套账号体系**：口令就是那同一个环境变量 `TUPING_ADMIN_TOKEN`。没设它时
`/admin` 回 404，而不是给出一张永远登不进去的表单，页脚也不出现那个链接——所以页面数据里 `Admin`
（这次请求带着会话）和 `AdminAvailable`（这个实例配了令牌）是两个字段。

**会话是签名的 cookie，不是服务端会话表。** 只有一个管理员，重启不该把人踢出去；而**签名覆盖自己的过期
时间**，所以 cookie 拿到手也改不长。签名密钥由 `TUPING_SECRET` 与令牌一起派生
（`derive(secret, "admin\x00"+token)`），于是**换令牌 = 所有已发出的会话立刻失效**。

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 有效期 | 12 小时 | 够在手机上收拾一晚上的聚会相册，又不至于把放在桌上的手机变成一把长期钥匙 |
| `HttpOnly` | 是 | 页面没有脚本，没有任何理由读它 |
| `Secure` | **否** | 局域网明文 http，带 Secure 的 cookie 根本不会回来（§10.1） |
| `SameSite` | **Lax** | 这就是 CSRF 的答案：浏览器不会把 Lax cookie 带在跨站 POST 上，而这里每一个会改东西的路由都是 POST。别人网页上的 `<img>` 既删不掉评论，也退不了登录——**这也是退出为什么是 POST 而不是一个链接** |

**`next` 必须校验。** 这是整个服务里唯一一页有人会**输入密码**，而开放重定向正是收密码的经典手法：链接
写 `/admin?next=…`，人输了令牌，浏览器在"本以为要回到自己那张照片"的那一刻被交给链接作者选的页面。只
接受本站的**路径**——以 `/` 开头、不以 `//` 开头（`//evil.example` 是主机名，不是路径，这就是全部的机关）、
不含 CR/LF——`GET` 与 `POST` 两头各过一遍。

**登录限流**：按 IP 每 10 分钟 20 次（`store.Allow`，与评论同一套固定窗口）。令牌是长随机串，所以这不是
让爆破无望的那道防线，而是不让一个坏脚本刷满日志和限流表的那道。

**没会话时会怎样**：任何管理员 URL（`GET` 或 `POST`）都 **303 到 `/admin?next=<这个 URL>`**，而不是 401。
401 在浏览器里是一条死路——没有可以按的东西——而这个重定向正是"登录完接着做刚才那件事"。登录成功就按
`next` 回去，人落在自己原本瞄着的那一页上。

**编辑是一张单独的页面。** 把 textarea 放在每条评论下面是另一种做法，代价是访客那一页（陌生人、手机、
站在电视前）为每条评论多长一个它永远看不到的表单。所以列表里每条评论只有两个控件，编辑通向
`/c/{code}/edit/{id}`：昵称 + 内容 + 保存，下面一个"删除这条评论"。编辑页同样是普通表单 POST + 303 回照片
页（PRG），失败时**保留已经打的字**——和访客表单同一条规矩（§10.1）。

**改动不过内容安全筛查，但仍然过长度。** 筛查回答的是"陌生人的话能不能公开"，而这里打字的人正是那个队列
往上汇报的对象：一个会拒绝管理员自己改错的审核工具没有用。**长度照旧管**——20 字是一台电视一行弹幕画得下
的量（§9.5），改超了就会在它要去的地方读不出来；空内容也拒。

**删除是软删除**（`status=3`），和 `POST /v1/admin/comments/{id}?action=delete` 是同一个决定：页面、弹幕历史
和评论数里都消失，行还留在库里，运营商能把它放回来。列表里**编辑是链接、删除是表单**，这个不对称是故意
的：改错了可以再改回来，删掉是一个决定；表单意味着这个请求是 POST，别的页面没法替人按下去。

**一条评论只属于一张照片。** `/c/{code}/edit/{id}` 里的 id 必须落在**这个短码的照片组里**（合并进来的旧 id
也算，§3.4）。审核接口按设计接受任何 id（§7 承诺的全局删除），但一个写着这张照片的 URL 不该能改到别的
照片上的评论——它重定向回去的那一页会显示一个并不包含这条评论的列表。

**管理员那一页剩下的部分照旧。** 登录后的同一个 cookie 也能打开 `/v1/admin/comments`（浏览器里不必再往地址
栏粘令牌）。审核队列本身这一版还是那个 JSON 接口，没有做界面；页面上的编辑／删除只覆盖**可见**的评论，
待审的那些仍然要经 `/v1/admin/*` 处理。

**没有 JS。** 登录、保存、删除各自都是一个普通表单 POST + 303 回一个 GET，§10.1 那条规则一字未改。

**已经飘在电视上的那条不会立刻变。** 电视端的历史拉取用 `since = 本地最新的 createdAt`
（`ReviewRepository.refreshComments`），而 `mergeComments` 只按 id **追加**、不更新已有的那条，于是：管理员
**改**过的那条，电视上正在飘的仍是旧文字（重新打开同一张照片也不会重取，因为 `since` 已经越过它）；管理员
**删**掉的那条，电视内存里那份还是 `status=1`，这一轮里会继续被重放。这不是这次改动引入的——§14 的"第三次
举报转待审"过去就是同一条路：状态变了，已经拿到手的副本不会因此消失。要让它在几秒内消失，得两边一起动：
服务端删除时往 live socket 推一条同 id、`status=3` 的消息（`liveMessage` 的形状已经有了），电视端
`mergeComments` 改成"同 id 覆盖"而不是"只追加"（`DanmakuFeed.canShow` 已经要求 `status==1`，覆盖之后它
自己就不画了）。**当天就按这两句话改了，并且在 Android TV 模拟器上验证过——见 §17.16。**

**在局域网明文 http 上，令牌是明文过网的。** 这没有改变 §10.1 的边界——这个实例本来就不能映射到公网——
但值得写在这里：网页登录让那个令牌多了一条浏览器可走的路径，而那条路径上默认没有 TLS。**§17.23 之后这条路
可以关掉**：设了 `TUPING_TLS_CERT/KEY` 之后，这条路径上的口令、会话 cookie、评论全都在 TLS 里，而 cookie
的 `Secure` 会自动跟上（明文部署下不设，否则那些 cookie 永远不会回来）。

**一条现场记录（2026-10-11 11:34）：** 服务器起来了、页面正常、评论能发，只是页脚没有 管理员登录。这读起来
像"最新代码没生效"，其实是新代码在**按设计工作**：没设 `TUPING_ADMIN_TOKEN` 就没有管理员，链接不出现、
`/admin` 回 404。根因是**启动时没带那个变量**——`tools/tuping.ps1 -Tasks run` 当时只是把它打印出来（一行空
的 `admin =`），从没设过它，所以本地按文档起的服务**必然**没有管理员。现在 `-Tasks run` 会自己生成一个并
打印 `admin = …` 与 `login = …/admin`；`docker-compose.yml` 那一行的注释也改成说清它的两面（设了 = 网页上
有登录，留空 = 没有管理员）。

**顺带一个诊断口诀**，写下来省下一次排查：`GET /admin` 回的是哪一页，就说明跑的是哪一版二进制。

| 回应 | 跑的是 |
| --- | --- |
| HTML 错误页「没有管理员接口」（正文里提到 `TUPING_ADMIN_TOKEN`） | **新**代码，只是没配令牌 |
| HTML 登录表单「图评管理员」 | 新代码，令牌已配 |

这条能成立，是因为新代码在没配令牌时是**自己渲染**那一页的：一个"没有管理员"的 404 也是一句话，而
Go 的默认 404 不会说话。这次就是靠它把"代码是旧的"和"开关没开"分开的。

**测试**：Go 侧 `TestAdminLoginAndCommentEditing`（访客页没有控件、未登录 303 到登录页并带 `next`、错令牌

### 17.16 幻灯片走不出第一页：查看器从不请求下一页（2026-10-11）

**现场**："幻灯片在播放的时候，播放五六十张之后，又从第一张开始播放。后边其实还有很多照片。播放的图片
后边的那些的缩略图还没有加载出来。"

**"五六十"这个数字就是答案**：`MainViewModel.PAGE_SIZE = 60`，网格一次取一页；那个相册是 217 张照片 +
6 个视频 = **223 项**。查看器手里的 `items` 就是网格当时加载的那一份，而 **`loadMore()` 在全项目里只有一
个调用点：`GalleryScreen` 的懒网格滚动检测**（`lastVisible >= size - 8`）。人一旦进了查看器，网格就不再
滚动，列表于是永远停在 60：放映在这 60 张里挑下一张，播完必然回到开头；第 61 项**从来没有被请求过**，它的
缩略图当然也不存在——同一个根因的两个症状，这也解释了为什么"后面的缩略图没加载出来"看起来像另一个 bug。

**改法**：把"该不该取下一页"提成一个纯函数 `needsNextPage(currentIndex, itemCount, showRunning)`
（`domain/NextPage.kt`），两个调用点共用同一个距离（`LOAD_MORE_DISTANCE = 8`，网格过去那份私有的
`PREFETCH_DISTANCE` 就是它）：

- **网格**：最后可见行距末尾 8 行以内就取——行为与原来逐字一致；
- **查看器**：**放映中无条件取**，因为随机放映的下一张来自列表任意位置，"指针接近末尾"这种判据根本不会
  可靠触发，而放映要走完的正是整本相册；手动翻页时用同一个 8 行距离（与网格同一条规则）。

一个值得记下的副作用：这个 effect 以 `items.size` 重新起跑，所以放映期间页面**一页接一页**到达，直到相册
末尾——与有人把网格滚到那么远所产生的请求完全一样，不是新的一类流量（每页只是一份元数据）。

**设备上验证**（模拟器，那个 217 张的共享相册）：

- **手动翻页**：第 50 次按键时读数 `51 / 60`（还没到触发线 52）；第 65 次时 **`66 / 120`** —— 列表自己
  长大，指针越过第 60 张而没有回头；
- **放映**：按下「幻灯片」后 **3 秒**，读数从 `120` 变成 **`223`**（相册全部项目）；19 秒后已经在
  **`192 / 223`**（随机顺序），不再在第 60 张循环。

**顺带一个导航坑**（对以后用遥控器复现的人有用）：信息条里 `原图` 在上一行、`图评` 与 `幻灯片` 在下一行
并排（实测坐标 x=747/y=858、x=1522/y=940、x=1686/y=940），而**当前这张已经在显示原图时 `原图` 按钮会被
移除**（§9.5 的规矩），所以"从左边数第二个按钮"这种按法会落空——按下前后的**文件名**是判断放映有没有真的
跑起来最可靠的指标（位置读数会变，但它只在信息条可见时才在无障碍树里）。

**测试**：`NextPageTest` 5 条——8 行的边界（51 不触发、52 触发）、放映中任意位置都触发、列表装不满一屏时
立刻触发、空列表永不触发，以及"落下一页把边界正好推后一页"（这条正是查看器那个 effect 能一页页连锁下去的
原因）。

### 17.17 删掉的评论从电视上消失：live socket 推的是"状态"，不是"事件"（2026-10-11）

**现场**（§17.15 收尾时记下的那条已知边界，当天就成了下一条反馈）："网页上删了评论，但是电视应用端正在显示
的评论不会消失，还在一直展示。"

**两个原因，各在一端。** 服务端只在**新评论**发生时推消息——编辑、待审、屏蔽、删除都不推；而电视端的历史
拉取是 `since = 本地最新的 createdAt`，编辑和删除都不移动这个值，所以那条评论在电视眼里从来没有变过。反过
来，电视端的 `mergeComments` **只按 id 追加**、不覆盖已有的那条：即便收到了新状态也会被丢掉。两头各错一半，
症状是同一个。

**改法：把 live socket 从"事件流"变成"状态流"。** 同一条 `{"t":"comment",…}` 现在在这些时刻都发：新评论、
被编辑、状态改变（待审 / 屏蔽 / 删除，网页端和 `/v1/admin/*` 两条路都算）、以及举报跨过阈值（§14）。客户端
于是只有一条规则——**按 id 覆盖我手里的那份**——而不是"新增"和"某条变了"两条路。`DanmakuFeed.canShow` 早就
要求 `status == 1`，所以覆盖成 3 之后它自己就不画了。

**`status` 从 `int` 变成 `*int`，这一处是必须的。** `0`（待审）是真实状态，而 `omitempty` 会把它整个丢掉，
客户端 `optInt("status", 1)` 就把一条被举报下架的评论读成"可见"——正好是反向的错。指针让"没有这个字段"
（ping）和"状态是 0"（待审）分开。

**状态发布寻址到照片的根 id**（`Store.RootID`）：电视订阅用的是它缓存的那个 imageId，也就是合并组的根，而
合并前写下的评论仍带着旧 id（§3.4）。按评论自己的 image id 发，恰好会漏掉这些——而"漏掉"看起来就是这次报
的那个 bug。

**删除仍然是软删除**：行还在库里，只是 `status=3`；页面、历史、评论数里都没有它。变的只是**已经把它拿在手
里的电视会被告知**。

**已经在飘的那一条会飘完。** 客户端没有去抽掉正在过屏的那条（那要动 feed 的 active/queue，得不偿失）：覆盖
之后列表里没有它了，重放循环（`LaunchedEffect(feed, photoKey, comments)` 以 `comments` 为键）随之重启，从
那一刻起不再 offer 它。它最多再走完当前这一趟（≤ 约 13 秒），然后再也不出现。

**测试**：

- **Go**：`TestLiveSocketPushesCommentStateChanges`（编辑推新文字、删除推 `status=3`）、
  `TestLiveSocketCarriesHeldStatus`（第三次举报推 `status=0`，且字段**必须存在**——它就是钉住 `omitempty`
  那个坑的）。三个 live 测试共用一个 `liveSocket` / `readLive` 助手。
- **Kotlin**：`mergeCommentStates` 从 `ReviewRepository` 里提出来成为一个纯函数（`CommentMerge.kt`），

### 17.18 缓存里有原图就直接画原图（2026-10-11）

**要的东西**："当预览图片时，如果缓存中有原图，则优先加载原图。"

**这条规则的理由只有一句：**「仅用于幻灯片播放」手动翻页时选缩略图，全部理由是**等**——下一张现在就要。
原图已经在磁盘上的时候，等是零，于是那条理由不成立，而画质白拿。所以这不是第四个设置项，是那条默认值在
它自己讲不通的那个角落里让一步。

**只让步给"等"，不让步给「否」。** `PreviewOriginal.wantsOriginal(slideshowRunning, originalCached)` 多了
第二个参数：`ALWAYS` 照旧是全真，`SLIDESHOW_ONLY` 变成 `slideshowRunning || originalCached`，**`NEVER` 仍然
是全假**。`NEVER` 的标签是「所有预览都是大缩略图」——它说的是**画什么**，不是**能取什么**；它同时还是给解不
动多百万像素的机器留的那条退路（§17.13 那次 OOM），因为"缓存里恰好有一张"就把 12MP 的 JPEG 塞给它是这台
设置存在的意义所要防的那种意外。测试里这条被钉住了：`PreviewOriginalTest` 现在有一条专门断言
`NEVER` 不被缓存命中翻盘。

**问磁盘是便宜的，所以问得起。** `MainViewModel.isImageCached(url)` 只做一次
`diskCache.openSnapshot(url)`——不联网、不解码、不进内存缓存——任何失败都答"没有"，也就是回到改动前的行为。

**在哪里问、问几张。** 查看器用一张 `id → 原图在不在` 的状态表（`cachedOriginals`），由一个 effect 在 IO 线
程上填：**屏幕上这张 + 往后 8 张**（`PROBE_AHEAD`，不是预取窗口那 50 张——这里不是下载，是 8 次 snapshot
open）。向前多问几张的意义是**翻过去的时候答案已经在了**：`stillUrlOf` 在指针停下时才决定 URL，如果那时才
开始问，每一次翻页都会先画缩略图再换。

**屏幕上这张走「原图」按钮那条路。** 前台那一层的 URL 是在问磁盘之前就定下的（打开查看器时、或上一个翻页
定下的），所以它的升级不重新指一次层，而是把 `originalRequest` 指向它自己——也就是**替用户按了一次「原图」**：
原图装到背后那一层，装好才换上来，中间不黑屏（§9.5 的两层机制）。只在设置本身没要求原图时这么做，否则等于
把已经在飞的请求重启一遍。效果是按钮会短暂地呼吸一下（`originalLoading`）然后消失，和真按下它一模一样。

**没有改的**：预取窗口仍然按设置取（`wantsOriginal` 不含缓存这一项）——已经在磁盘上的原图不需要预热，而窗
口顺带下的那张缩略图只是小浪费；网格仍然只画缩略图，这条规则说的是"预览"。

**设备上验证**（Android TV 模拟器、mock NAS 供图、默认设置 `仅用于幻灯片播放`、手动翻页）：

| 步骤 | 无障碍树里读到的 |
| --- | --- |
| 冷缓存打开 `IMG_20260930_10` | `缩略图` + 「原图」按钮（改动前就是这样） |
| 按下「原图」 | `原图`，按钮消失（原图进了磁盘缓存） |
| 向右翻到 `IMG_20260930_09`（从没取过原图） | `缩略图` + 「原图」按钮 ← **反向对照** |
| 向左翻回 `IMG_20260930_10` | **`原图`**，没有按钮 ← 没人按过任何东西 |
| 退出查看器再打开同一张 | **`原图`** ← 打开时那条升级路径 |

**测试**：`PreviewOriginalTest` 6 条（新增"缓存命中在手翻时生效、对「否」不生效"，以及"新参数的缺省值让每一
个老调用点含义不变"）。判定逻辑是纯函数，磁盘探查是薄薄一层——这条规则的证据因此不依赖模拟器，模拟器只是
把它在真屏幕上走了一遍。

### 17.19 签名密钥不再由人来填（2026-10-11）

**触发的问题是这一句**："我设置了这个值，但是我又没有在任何地方去使用修改它，这个设置就是多余的呀。"
问得对，而且指出的正是文档的毛病：`TUPING_SECRET` 从来不是给部署者操作的开关，它是**服务器每次请求都在用**
的钥匙——缩略图 URL 的签名（10 分钟）、管理员 cookie 的 MAC（12 小时）、评论里 IP 的 HMAC——只是它一辈子
不出现第二次，于是在"三步部署"里读起来像一句没人念的咒语。§11.5 说它必填的理由是"启动时随机生成会让每次
重启都换钥匙"，那条理由成立，但它只否掉了**易失**的生成，没有回答"为什么必须由人来填"。

**它真正的要求只有两条**：外人不能知道、重启后不能变。两条都不需要人参与，所以 `TUPING_SECRET` 变成可选
（`internal/secret`）：

| 情形 | 取值 | 启动日志 |
| --- | --- | --- |
| 设了 `TUPING_SECRET` | 用它，不碰文件 | `signingKey=TUPING_SECRET` |
| 没设，文件在 | 读 `TUPING_SECRET_FILE`（默认数据库同目录的 `secret`） | `signingKey=file` |
| 没设，文件不在 | 生成 32 字节随机值，`0600` 写进那个文件 | `signingKey=new` + 一行 WARN |

**为什么文件放在数据库旁边**：那个目录本来就必须跨重建存活、本来就在备份范围内（§11.5）。写入用
`O_EXCL` + `fsync`，于是两个容器同时首次启动也只会有一个赢家，赢家的值就是两者的值；空文件按"写到一半崩了"
处理——换一个新的并 WARN（没有哪个会话可能依赖一个从未可用的密钥）；读不了的文件是**硬错误**——读不到自己
钥匙的服务器不许拿另一把钥匙启动。

**明确否掉的替代方案是"令牌 + 固定串"**（提问者本来想这么干，它确实能让人只填一个值）：`adminSecret` 是
`derive(secret, "admin\0"+token)`（§17.15），cookie 就是它的 MAC，于是 SECRET 一旦是令牌的函数，**截获一个
cookie 就等于拿到一个可离线爆破的口令**——而 cookie 走的是明文 http。两个值独立时，同样的截获最坏只是
"12 小时后自动失效"。所以"让别人只填一个值"这件事应该由服务器自己做，而不是把口令提升成签名根。README 的
「签名密钥」一节把这段写给部署者看。

**测试**：`internal/secret` 9 条——显式值优先且不写文件、首次生成并持久化、重启读到同一个值、文件权限
`0600`（Windows 上跳过：那里不强制 POSIX 位）、已有文件原样使用（含首尾空白）、空文件被替换、读不了是错误、
8 个并发启动拿到同一个值、`Inspect` 不创建文件。设备上一次端到端（本机跑 `-check` 与真实启动）：首次启动
WARN + `signingKey=new` → 重启 `signingKey=file` 且文件字节不变 → 设了 `TUPING_SECRET` 时
`signingKey=TUPING_SECRET` 且那个文件一动不动。

### 17.20 地址也不再由人来填：二维码的兜底从"配置"改成"调用者"（2026-10-11）

**触发的问题是同一句话的第二次**："这个 TUPING_BASE_URL 也删掉呗。" 上一节（§17.19）把签名密钥交还给服务器，
这一节把地址交还给**正在连接的那一端**——而 §17.6 早就证明了它比配置更可信：服务端不知道电视是从哪个地址找
过来的，而电视知道自己刚刚用哪个地址连通了。

**改法**：`TUPING_BASE_URL` 从必填（`configFromEnv` 里那条 `TUPING_BASE_URL is required`）变成可选的钉子，
地址按三档取：短码上记着的（电视上报的）→ `TUPING_BASE_URL` → **这次请求的 Host 头**。第三档和第一档是同一类
证据（都是"某台设备刚刚用过的地址"），只是不那么明确，所以它**从不落库**：它回答的是"你从哪儿连过来的"，
不是"这张码以后该指向哪儿"。

**与 §17.6 的关系（这条必须写清楚）**：§17.6 那句"不是信任 Host 头"针对的是**把 Host 当作短码的地址来源存
下来**——那是任何人随便填的，一旦落库就跟着二维码印出去。这里的 Host 只用于**这一次响应**，不落库，并且：

- `127.0.0.1` / `localhost` / `[::1]` / `0.0.0.0` 一律不算证据（`isLoopbackHost`）；
- 内容依赖 Host 时，`Cache-Control` 从 `public, max-age=86400, immutable` 收紧成 `private, no-store` ——
  同一条短码在不同 Host 下内容不同，共享缓存把它发给另一个域名的客人就是新造的一个 bug；
- 三档都没有时**拒绝渲染二维码**（400，并写明两条出路），而不是把 `/c/<短码>` 编进去。

**H5 页面反而更结实了**：没有可用地址时缩略图退化成相对路径 `/t/<短码>?…`，浏览器按页面自己的来源解析 ——
局域网、端口映射、反向代理，页面里的图一定是通的。以前"服务端配的地址把客人的图打碎"那条路径，现在连兜底
值都不存在了。

**留下的钉子**：反向代理改写 Host、或老客户端不报地址时，`TUPING_BASE_URL` 仍是唯一能钉住答案的地方，所以它
留着，只是不再必填。`POST /v1/devices` 回包里的 `baseUrl` 也从"配置值"变成"配置值，否则就是这次请求的地址"，
那是新电视设置项的默认值。

**测试**：`baseurl_test.go` 新增 6 条——`isLoopbackHost` 的分类（含容器名与 `.local` 不算 loopback）、无地址
无上报时二维码用调用者的地址且 `no-store`、loopback 下二维码 400 而评论页退化成相对 URL、钉住的值压过调用者
（且仍可缓存）、新设备回包里是"它刚用过的地址"、`/healthz` 用 `baseUrlSource` 说明 `baseUrl` 为空的原因。
设备上一次端到端（本机跑真实二进制，既没设 `TUPING_BASE_URL` 也没设 `TUPING_SECRET`）：`-check` 说明两个默认
→ 启动日志 `signingKey=new` + `TUPING_BASE_URL is not set` → `/healthz` 报
`"baseUrl":"","baseUrlSource":"the address each caller used"` → 以 `Host: 192.168.31.51:8080` 注册设备，回包的
`baseUrl` 就是它 → 注册一张**不上报地址**的照片，回包的 `qrUrl` / `thumbUrl` 都落在
`http://192.168.31.51:8080/…` → 同一个短码以 `Host: 192.168.31.51:8080` 取二维码，得到
`X-Page-Url: http://192.168.31.51:8080/c/…` 与 `Cache-Control: private, no-store`；以 loopback 取则 400
`no_address`，而 `/c/<短码>` 依旧 200，且 `<img src="/t/…">` 是相对路径。

### 17.21 部署者不该知道 uid 是什么：启动时接管数据目录，然后放弃 root（2026-10-11）

**触发的问题是这一句**："这就是一个公开的仓库，需要非 root，如果用户要部署这个项目，除了改 admin token，
还要执行个什么命令吗？太麻烦了，我就想让改个 admin token，然后启动就行。" 而第一次真实部署撞上的正是这条
（`tupingd: store: migrate: unable to open database file (14)`）：容器里的进程是 uid 10001，bind mount 的宿主
目录是 Docker 以 **root** 建的，权限检查比的是数字，SQLite 连文件都建不出来。

**这两件事都得成立，而它们互相冲突**：镜像必须非 root（公开仓库、要解析用户上传的 JPEG，将来某个解析 bug
被利用时不该直接落到 root），部署者必须一个命令都不用敲。冲突只能用"短暂地拥有 root，然后彻底放弃"来解，
也就是 postgres / redis / mysql 那些镜像早就用的形状：

1. 镜像**不再写 `USER tuping`**，进程以 root 启动；
2. 二进制在打开数据库之前，把 `TUPING_DB` 所在目录与 `TUPING_THUMBS`（含里面已有的文件）的属主改成
   10001:10001 —— 顶层目录的属主已经是 10001 就整棵树都不走（第一次启动之后每次启动都是这条快路径）；
3. 紧接着 `setgroups` → `setgid` → `setuid` 到 10001，顺序不能换：先降 uid 就会失去改 gid 的资格，而漏掉
   setgroups 会留下 root 的附加组；
4. 这之后才 `store.Open`，所以数据库、缩略图、以及 §17.19 那个 `secret` 文件全都是 10001 建的。

**权限窗口有多大**：从进程启动到 `store.Open` 之间，几毫秒，没有监听套接字、没有解析任何输入。对外服务的
pid 永远是 10001 —— 日志里有一行 `running unprivileged uid=10001 gid=10001`，`/proc/<pid>/status` 里也是。

**失败时不拒绝启动**：`chown` 失败（SMB/CIFS 这类不支持的文件系统）只记一行 WARN 并**保持 root** —— 那种
部署里 root 照样能写，把服务拒之门外才是更糟的结果。compose 里的 `# user: "0:0"` 就是给这种场景留的显式开关，
也是平台强制了 `user:` 时唯一能用的一条路（那时进程本来就不是 root，接管这一步自动跳过）。

**部署者的动作因此只剩三个**（改 admin token、传四个文件、建项目并启动）：README 第 4 步留着，但它讲的是
"不用你做"和那两行日志的含义，而不是一条 chown 命令。

**测试**：`priv_test.go` 两条——`writableDirs` 覆盖默认布局／thumbs 与库同目录／未配置 thumbs 三种输入；
以及一条**跨文件不变量**：Dockerfile 里必须仍有 `-u 10001`、且不得再出现任何 `USER ` 指令（正是"两边那个
数字必须一致，而镜像必须从 root 起步"这两条，否则要么默默以 root 服务、要么写不出数据库）。在真实 Linux 内核
上（WSL Ubuntu，x86_64）跑了一遍完整流程：

| 场景 | 结果 |
| --- | --- |
| 数据目录 root:root 0755，里面还有一个 root 建的 `left-by-root.jpg`，以 root 启动 | 日志先 `running unprivileged uid=10001`；`/proc/<pid>/status` = `Uid: 10001 10001 10001 10001`；`tuping.db` / `-wal` / `-shm` / `secret`(600) / `thumbs/` 以及那个老文件全部变成 10001:10001；`/healthz` 200、`/admin` 200、SIGTERM 干净退出 |
| 同一个目录再启动一次 | 依旧 `running unprivileged`，`signingKey=file`（读到同一把密钥，没有重新生成），数据库沿用 |
| 以 `nobody` 起、目录属于它（开发者本机那种） | 没有 `running unprivileged` 那行（本来就没 root），正常服务，healthz 200 |

### 17.22 部署收敛成一份文件：镜像发 Docker Hub，多架构（2026-10-11）

**触发的问题**："为什么这么复杂，能不能改一下方案什么的，用户只需要拿一个 docker-compose.yaml 文件，
然后构建就可以了。"

**先把复杂度归位**：四个文件（compose / Dockerfile / .dockerignore / 二进制）不是这个项目发明的，而是
"compose 里写 `build: .`"的必然结果 —— 有构建就必须有配方和料，而且必须在同一个目录里。§11.5 当初选择
不发镜像的理由是"国内拉 Docker Hub 和 ghcr.io 都不稳，而本地构建只拉一个 3 MB 的 alpine"。**这条理由在
2026-10-11 的第一次真实部署里被证伪**：那次构建正是卡在 `FROM alpine:3.20`（镜像源 401、直连被重置）。
也就是说本地构建**照样依赖 registry**，省下的只是"我们发不发镜像"，代价却全落在部署者身上：认架构、
下 15 MB 二进制、四个文件同层、还要分清「构建」和「启动」。

**改成**：镜像发布在 Docker Hub，**多架构**（`linux/amd64` + `linux/arm64` 打进同一个 manifest）。部署者
拿到的是一份 compose：

```yaml
services:
  tuping:
    image: <namespace>/tuping:0.1.0
    restart: unless-stopped
    ports: ["8080:8080"]
    volumes: ["./data:/data"]
    environment:
      TUPING_ADMIN_TOKEN: "<口令>"
```

三件事一起消失：不用挑二进制（架构由清单决定）、不用 Dockerfile（没有构建）、不用管「构建 vs 启动」
（只有拉取）。`TARGETARCH` 顺带删掉了 README 里"ARM 上要把文件重命名成 amd64"那条要求 —— 那是
`COPY tupingd-linux-amd64` 写死文件名的副作用；BuildKit 没有定义 `TARGETARCH` 时构建会**明确失败并指出
它想要的文件名**，这比默默选 amd64、然后在容器日志里留下 `exec format error` 好。

**发布怎么走**：`.github/workflows/server-image.yml`，在 `server-v*` tag 上跑：vet + test → 交叉编译两个
架构（与 `tools/tuping.ps1 -Tasks dist` 同一组产物）→ buildx 多架构构建并推送 → 把同一套文件附到 release
上（顺手补上 §17.21 里记的那个"服务端从来没有 release"的缺口）。需要两个 repo secret：
`DOCKERHUB_USERNAME`（同时充当镜像命名空间，所以没有第三处要同步）与 `DOCKERHUB_TOKEN`；第一次 push
会自己创建公开仓库，不必事先建。CI 里**没有**调用 `tools/tuping.ps1`：那个脚本钉死了国内 GOPROXY 和
Windows 的工具链根目录，两样在 GitHub runner 上都是错的 —— 代价是 go build 的 `-ldflags` 在两处各写一遍，
所以两边注释互相点名。

**自建这条路保留**：`docker-compose.yml`（`build: .`）和那四个文件照样发 —— NAS 出不了外网、想改
Dockerfile、想自己审计镜像的人都用得上，release 附件里也是同一套。两条路只在"镜像从哪来"上不同。

**边界**：镜像里的东西一点没变（alpine + 15 MB 静态二进制 + 启动时接管属主再降权，§17.19／§17.21），
变的只是它从哪儿来。国内拉 Docker Hub 仍然要加速源，但那和"构建要拉 alpine"是同一个开关，所以没有
新增一类故障。

### 17.23 服务端自己会说 HTTPS，证书不归它管（2026-10-11）

**触发的问题是这一句**："图评服务器现在是 http 的，能不能弄成 https 的。"问下去之后那句更关键：
"我只要应用能支持 https，至于怎么映射域名、怎么穿透、怎么弄证书，这是部署这个服务的人自己要去做的事情。"

**先把分工定下来**：证书的**获取**需要域名、公网 80 端口或者 DNS 服务商的 API，还要一个定时续期的东西；
而部署这个服务的人**已经有**了 —— 他的 NAS 上多数还跑着别的服务，ACME 客户端、反代、隧道都是他自己选的。
所以这一节只做三件事：用给的两个文件提供服务、文件被换掉之后自己重读、只给了一半的时候大声失败。

**为什么不内置 ACME（`autocert`）**：那会把"这个二进制自己就能拿证书"变成一句承诺，而它成立的条件是
"有域名 + 80 端口可达（或用 DNS-01 就得再带一个 DNS 插件依赖）+ 这台机器能被 Let's Encrypt 找到"。三个条件
里任何一个不成立，失败都发生在**签发阶段**，而部署者看到的是"服务没起来"，不是"证书没签下来"——又一个
症状和原因分家的故障。分工的价值在于：证书坏了，是 ACME 客户端的报错；协议坏了，是这个二进制的报错。

**为什么不要求必须挂反代**：反代终止 TLS 是最常见的做法，而且**不需要改这个服务端**（电视上报自己的地址，
那里本来就是 https；不报的话钉 `TUPING_BASE_URL`）。所以 README 把这条路照样写着。但把它变成义务是不对的：
§17.22 刚把部署收敛成"一个二进制 + 一份 compose"，再加一句"你还得会配 nginx"就是把它退回去。

**改法（两个变量，必须成对）**：`TUPING_TLS_CERT` / `TUPING_TLS_KEY`，都是文件路径。只设一个**在启动时
拒绝**并点名缺的那个 —— 悄悄退回明文是这里唯一不可接受的失败方向：那会让"证书配好了"这件事在每一块屏幕
上都看不出来，而管理员口令正从局域网里明文过网（它只保护**传输**，不改变 §10.1 的边界）。

**证书热重载，而不是 `ServeTLS(l, certFile, keyFile)`**：后者只读一次。ACME 的续期是定时的、无人值守的，
盘上的文件换了而这个进程继续用旧的 —— 症状在某一天突然出现在客人的手机上，而容器从面板看一切正常。
所以用 `tls.Config.GetCertificate` 指向一个每分钟重读一次的加载器（两个小文件、一分钟一次，成本可以忽略）。
**失败方向是有意的**：新的读不出来就继续用旧的并记一行 error —— 一次写坏的续期不该把服务弄停，而旧证书在
它自己的到期时间之前一直是有效的。启动时和每次重载都记下 `notAfter`，到期前 14 天 WARN，已过期 ERROR：
这是部署者从容器里面唯一看不见的证书问题。

**连接决定协议，这一条不用改代码**：`callerBase` 本来就读 `r.TLS`（§17.20），所以同一份服务端，用明文访问
得到 `http://…` 的链接，用 TLS 访问得到 `https://…`；二维码里的地址本来就是电视上报的"它刚用过的那个"，所以
电视端把地址改成 `https://` 之后整条链就都是 https。**不读 `X-Forwarded-Proto`**，理由和 `clientIP` 不读
`X-Forwarded-For` 一样（§10.1）：那是任何调用者都能填的头，让它决定二维码里印什么地址，等于让陌生人替电视
选地址。反代终止 TLS 的场合钉 `TUPING_BASE_URL` 就行。

**cookie 的 `Secure` 跟着连接走**：明文部署下不设（§10.1 早就说过，Secure cookie 在 http 上永远不回来，
"设上"会把昵称、访客身份、管理员会话一起静默删掉）；TLS 下必须设 —— 那个 cookie 是整个实例所有评论的
bearer token（§17.15）。同一个判断在三个地方用，成了一个 `cookieSecure(r)`。

**`/healthz` 多说一个字段**：`"tls":true|false`，这是部署者从 NAS 面板里唯一确认不了的事。另外新增一类
告警：TLS 开着而 `TUPING_BASE_URL` 钉的是 `http://` —— 那个端口已经不说 http 了，二维码和链接全部指向一个
没人应答的地址，而电视上什么都看不出来。两种告警现在会同时出现（私网地址 + http 钉死），所以 `warning`
字段改成把多条拼起来，而不是后一条盖掉前一条。

**健康检查改成二进制自己探测（`-health`）**：镜像里没有 curl，busybox 的 wget 有没有 TLS 支持取决于构建，
而且**真证书从来不是签给 127.0.0.1 的** —— 用 `wget https://127.0.0.1:8080/healthz` 探一个 TLS 部署，
结论永远是"不健康"，而那是一个完全正常的部署。所以探针是这个二进制问自己：它按同一套环境变量算出协议和
地址（`:8080` / `0.0.0.0:8080` 这类监听地址不是可拨号的地址，换成 `127.0.0.1`），退出 0/非 0 并说明打不开
哪个 URL。顺带的好处是它也能在容器里手敲：`docker exec tuping tupingd -health`。
`docker-compose.image.yml` 里那一条**两段式**（`tupingd -health || wget http://…`）是有意的：
第一段让配了证书的新镜像健康，而且因为 `-health` 知道协议，它不会每分钟往容器日志里留一行失败的 TLS
握手；第二段是给已经发布的 0.1.0 镜像的兜底 —— 那个版本还没有 `-health`，而它在明文 http 上直接就能答。

**测试**：`tls_test.go` 三条 —— 成对规则（含"只有空白"算没设）、**热重载**（换掉两个文件之后真的换了证书；
中间塞一个写坏的文件时继续用旧的）、坏路径/不成对的失败信息点名环境变量；热重载走的是**真实握手**
（`tls.Server` + `tls.Dial`），因为直接调 `GetCertificate` 只能证明重载逻辑，证明不了"crypto/tls 真的会问它"。
`selfcheck_test.go` 三条 —— `probeURL` 的地址翻译、明文/TLS 两种探针各自成功与互相失败、非 200 不算健康。
`api/tls_test.go` 四条 —— 访客 cookie 与管理员 cookie 的 `Secure` 在两个方向上都对、**链接跟随连接**
（TLS 监听 + `Host: 192.168.31.51:8443` 取二维码，`X-Page-Url` 是 `https://…`）、`/healthz` 的 `tls` 字段与
http 钉死地址的告警。

设备上一次端到端（本机跑真实二进制，自签证书 `CN=tuping.test`，`TUPING_ADDR=127.0.0.1:8443`）：

| 动作 | 结果 |
| --- | --- |
| `curl -k https://127.0.0.1:8443/healthz` | `{"ok":true,"tls":true,…,`baseUrlSource":"the address each caller used"}` |
| 同一端口上发明文 HTTP | 400，日志一行 `client sent an HTTP request to an HTTPS server` —— 这个端口不再说明文 |
| `openssl s_client -servername tuping.test -alpn h2` | `subject=CN=tuping.test`；**`ALPN protocol: h2`**（HTTP/2 是 `ServeTLS` 白给的） |
| 进程运行中把两个文件换成 `CN=tuping.test-RENEWED` | 69 秒后同一次握手就是新证书，日志 `reloaded the certificate subject=tuping.test-RENEWED`，**进程没有重启**（PID 未变） |
| `tupingd -health`（TLS 监听） | 退出 0 |
| `tupingd -check` | `tls = on (cert=… key=… subject="tuping.test-RENEWED" notAfter=2027-01-09T12:06:33Z)` |
| 只设 `TUPING_TLS_CERT` | 退出 1：`TUPING_TLS_CERT is set but TUPING_TLS_KEY is not: set both, or neither (neither serves plain http)` |
| 不设 TLS 变量重跑（明文默认） | `"tls":false`，`-health` 退出 0 —— 默认那条路一点没变 |
| `tupingd -health` 指向没人监听的端口 | 退出 1 并写出 `no answer from http://127.0.0.1:9/healthz` |

**留给部署者的一句话**（README 里也写了）：自签证书在这套配置下**技术上是通的**，但二维码是给客人的手机扫的
—— 微信会拦住不受信任的证书，所以想要绿锁就得是真证书。服务端不替这个选择负责，它只保证配什么就说什么。

**补记：第一次真实反馈暴露的两件事（2026-10-11 晚）**。反馈的原话是"为什么我配置了 https，但是 http 生效了，
https 没生效"，两件事都不是代码错，但都得记下来：

1. **特性有版本，而文档当时没写。** 这个特性是 **0.1.1** 才有的：0.1.0 的镜像（tag `server-v0.1.0` →
   `de32a60`）里没有这段代码，**旧二进制不认识这两个变量，既不生效也不报错** —— 端口照旧说明文 http，用
   https 连过去只得到一个 400。而 README 把 HTTPS 的写法直接贴在 `image: …:0.1.0` 下面，照着做的人必然踩到。
   这和 §17.19／§17.20 的教训是同一个形状：**沉默的配置比报错的配置贵得多**。所以文档里补了两件东西：
   一句**前提**（这个特性从哪个 tag 起有），和一条 30 秒的确认命令
   （`docker exec tuping /usr/local/bin/tupingd -check | grep '^tls'` —— 有输出就是认识，一行都没有就是
   二进制太旧；面板日志里 `tupingd listening` 那行的 `tls=` 字段是同一件事）。另外"环境变量改了必须点
   **启动 / 重新部署**、只点「重启」不算"这句，原来只出现在升级那一节，现在也写进了排障表。
2. **README 里给人粘贴的 YAML 会被复制链路重排。** 实测的断点很有规律：**未加引号**的值里出现 `:` 或 `-`
   就被拆成两行（`kungfucode/tuping:0.1.0` → 两行，`unless-stopped` → `unless-` + `stopped`），而同一页里
   **带引号**的 `"8080:8080"`、`"change-me"` 原样通过。所以那几段现在是"每行都短 + 每个值都带引号"，注释
   一律搬到正文；`readme_test.go` 用两条测试守着这两个属性（行宽 ≤ 60、值必须带引号），免得下次写文档的人
   再把它们带回来。粘贴这条路本来就不该是部署的必经之路 —— 文档里同时也给了"把 compose 文件传进目录、
   按路径建项目"这条不用粘贴的路。

### 17.24 电视上那张二维码来自上一台服务器（2026-10-11 晚）

**现场**："我构建了新的 server 端，扫码后提示这张照片不在图片数据库里"（H5 页的原话是「这张照片不在图评里」，
`api/pages.go` 的 404）。三个测量一起指向同一件事，而且都不是"服务器坏了"：

- 新服务器的 `/healthz`：`uptimeSec:331`、`thumbBytes:0`。缩略图目录是空的，也就是说它的 `data/` 是新的；
- 电视端的日志（11:52:46，与新服务器起来的时刻同一分钟）：`图评: … does not accept this device's token;
  registering again` → `服务器出错了` → `live socket closed: Expected HTTP 101 response but was '404 Not
  Found'`。设备重新注册成功了，但**照片没有**；
- 电视缓存里的两个短码，对着新服务器取回来都是 **404**；`cache/review-qr` 里最后一个文件的时间是 06:18
  —— 也就是说重新注册这台设备之后，它一张照片都没重新注册过。

**根因是 §17.7 那道修复只修了一半。** 1.4.2 为"服务器不认得这台设备"写了修复：拒绝令牌 → 丢掉凭据 → 领一个
新设备。而它的注释**明确地**保留了照片侧的一切，理由是：内存里的身份是"服务器对照片的回答"，用服务器自己的
image id 做键，一张照片被新设备重新注册之后会回到同一个身份（指纹层就是干这个的）。这句话在服务器**还持有
那些行**的时候是对的 —— 而这道修复存在的全部理由，恰恰是重装、恢复到旧备份、或换了 data 目录之后它不持有。
于是电视继续画着新服务器从没签发过的码，扫码落到 H5 的 404，而屏幕上没有任何东西、应用里也没有任何一次按键
能从里面出来（除非重启进程，那只是把内存里的缓存清掉）。

**改法：一次修复要连"旧服务器的回答"一起丢掉。** 设备被拒 = 服务器说它从没听说过这台电视；这句话不是关于
令牌的，是关于**那台服务器**的：手里的短码、image id、评论都是它签发的。所以新设备到手之后立刻丢掉
`identities`、`commentCache` 和磁盘上的 QR PNG（`review-qr/`），并把**屏幕上那张**重新注册一遍 —— 新码顶掉
死码，中间不黑屏。重新注册一张已经存在的照片在服务端是廉价的：同一份字节回到同一个身份，这正是指纹层的作用。

**同一个结论还有另一扇门，而且不需要拒绝令牌。** 历史读（`GET /v1/comments?imageId=…`）对这个服务器没有
的照片答 `not_found`。它和"拒绝令牌"是同一件事的两端：服务器只恢复到"设备注册之后、这张照片注册之前"的备份
时，设备照样被接受，而这一张照片不在。所以 `not_found` 也丢掉**那一张**的身份并重注册它 —— 每张照片只做一次
（`healedPhotos`），因为一个"对刚交给它的照片也答 404"的服务器有 bug，而照着它无限重注册就是这端的 bug 了。
两个判断都收进了新文件 `data/review/DeviceRepair.kt`，因为它已经是"只能被真 socket 证明"的那一类东西。

**一处刻意的顺序**：只有当屏幕上是 `Ready`（也就是说**有一张码在屏幕上**）时才重注册。正在注册中的那张不算
—— 它正在对着"服务器还认得它"这一前提注册，再问一次会给一张图签出两个码、取两张 QR。这不是理论上的重叠：
被换掉的服务器会让上面两条结论同时成立（修复之后的第一次重试，历史读回的就是 `not_found`）。

**设备上还没有走完。** 报告是用户在真机上遇到的、我们已经用同一台服务器的真实回答定位到根因（上面三个测量），
但"装上 1.4.11 之后这张码自己换掉"这一步没有在电视上跑过 —— 计划是拿 `tools/mock-review` 演一遍换服务器的
过程（注册 → 杀掉 mock → 重启一个空的 → 看它自己重新注册）。`ReviewRecoveryTest` 的 6 条覆盖的是判断本身：
拒绝令牌的修复会且只会报告一次"服务器被换掉了"、掉包不算拒绝、领不到设备的拒绝不算换服务器、两个调用同时被
拒只领一个设备、历史读的 `not_found` 是"服务器没有这张照片"、以及其余协议回答都不是。

**给部署者的一句话**：APK 的这一改只会让电视**自救**，它变不回服务器的数据。换 data 目录（或删掉它）就是
评论全没了，而电视在下一次打开照片时会安静地重新注册 —— 屏幕上看起来会像"评论都没了"，而不是"服务器坏了"。

### 17.25 发评论端点自己的额度：120 条/分（2026-10-11 晚）

**要求**："加个限制，添加评论的 api 一分钟最多调120次"。§7 那张表里原本有三道按调用方算的额度（每个访客
5 条/分、50 条/天，每个 IP 30 条/分）和一道按图算的（200 条/小时），而**按调用方算的额度全都可以靠换一个身份
绕开**：清 cookie 就是新访客，换出口 IP 就是新地址，换一张图就是新图。公网部署上这是实际发生的事，所以
120 这条按**端点**算：键是固定的 `cmt-service:min`，`store.LimitPerService`，`handleCommentCreate` 与 H5
表单 `handlePageSubmit` 共用同一个键（两条路创建的是同一种东西，只数一条等于只封了半个服务）。

**它是最松的一档，这是有意的。** 前三道额度只会拒绝"正在刷屏的那个人"，而这一道会拒绝"没有做错任何事的人"
—— 全局 2 条/秒，家庭聚会到不了这个数；单个刷屏者仍然由 30/分 和 5/分 先拦住。检查顺序上它排在**第一位**，
这样"服务满了"这种与调用方无关的拒绝不会顺带把调用方自己的额度也扣掉（`AllowAll` 是按顺序逐个扣的）。

**测试的形状**：`TestCommentBudgetIsWholeService` 用五个回环源地址（`127.0.0.1`–`127.0.0.5`，每个各自
30/分的 IP 额度）和每条请求一个新 `anonId`（每个访客各自 5/分），谁都没有超自己的线，端点仍然在第 121 条上
拒绝。这是唯一能看见它的形状：单个地址根本走不到 120，因为它在 30 就被自己的 IP 额度拦住了。变异检查做过：
把 handler 里那一行注释掉，同一份测试报 `the endpoint took 122 comments, want exactly 120` 并失败。
