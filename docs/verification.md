# 验证记录

这份文档记的是**每一项功能是怎么验的** —— 读数是什么、在什么设备上、以及过程中抓出来的 bug。
它从 README 里搬出来，因为用应用的人不需要读它，而改代码的人需要。

- 功能怎么用：[`../README.md`](../README.md)
- 项目结构与构建：[`DEVELOPMENT.md`](DEVELOPMENT.md)
- 下面每条里的「第 N 条」相互引用，编号沿用历史顺序。

---

在这里没有办法拿封闭协议对着真机做单元测试，所以验证是刻意搭起来的：

1. **一个真正强制实施规则的飞牛模拟服务器** —— `tools/mock-nas`。和参考项目自带的 mock 不同，它会校验 `authx` 签名、拒绝数字形式的 `si`，并且可以在运行时被固定到任一签名规则。它同时提供**两种**传输：5666 上的明文（`verify.js` 驱动的就是它，也是最容易直接读原始流量的）和 **5667** 上的 TLS，用的是自签名 `O=fnOS CN=fnOS` 证书、`subjectAltName` 为 `DNS:fnOS` —— 与真实 NAS 呈现的形状一致，所以客户端的首次使用信任路径是被真正走了一遍，而不是绕过。把应用指向 `10.0.2.2:5667` 即可对着这个 mock 运行。它发的照片是 `tools/mock-nas/assets/photos/` 里那 60 张**真照片**（`node fetch-photos.js` 拉的，Unsplash 授权，来源逐张记在旁边的 `CREDITS.md` 里）—— 从前的 mock 是一张照片一个渐变色块，断言缩略图有没有到达够用，但那样的截图没法拿给人看。
2. **一个独立的参考客户端** —— `tools/mock-nas/verify.js` 从零重新实现该协议，断言匹配的那条规则被接受、不匹配的那条以 `5000` 被拒绝，并断言登录握手在 TLS 端口上的 `wss` 可用。在相信任何从 mock 得出的结论之前先跑它：

   ```powershell
   cd tools/mock-nas
   npm install
   node server.js          # 终端 1
   node verify.js          # 终端 2
   ```

   它已经抓到过 mock 自身的一个真实 bug（编码后的候选中多带了一个客户端并不会签名的前导 `?`）。
3. **在 Android TV 模拟器上跑真机** —— 每个屏幕和遥控器动作都对着 mock 走了一遍，截图留在本地 `artifacts/screenshots/`（**未入库**，重跑一遍应用即可再生成）。
4. **协商签名测试** —— 把 mock 固定到客户端**不会**一开始采用的那条规则，请求被拒绝，客户端翻转规则、重试、成功，并持久化该选择。通过读服务器计数器和应用存储的偏好两处确认。
5. **地址归一化的单元测试**：`& .\tools\build.ps1 -Tasks testDebugUnitTest`。它们抓到过一个真实 bug：`trimEnd('/')` 把 `http://` 变成了 `http:`。
6. **图评：服务端单测 + 端到端契约测试** —— `server/` 是一个 Go 模块，所以它可以被真正地测：`& .\tools\tuping.ps1 -Tasks test` 跑 `phash`（用 `tools/mock-nas` 里那批**真照片**：重编码是 0 位、裁剪救不回来、扁平图互相碰撞、EXIF 方向在算指纹之前就被扭正）、`store`（同一份字节是一个身份、补边的副本会通过剥边回到同一个身份、评论在合并后不搬家、解绑把评论还回去）和 `api`（一次 `httptest` 里走完注册 → 二维码 → 签名缩略图 → 评论 → WebSocket 推送 → 举报 → 审核 → 删除）。这条路里有两个 bug 是测试抓出来的，不是读代码看出来的：
   - 日志中间件包了一层 `http.ResponseWriter`，把 `http.Hijacker` 挡住了 —— 每一个 WebSocket 升级都以 **501** 收场，而电视上的表现只会是"弹幕永远不来"。
   - 剥黑边之后的候选指纹，画幅比例却仍然拿**原图**去比 —— 于是"聊天软件补过边的那份"永远进不了候选集，而那正是整个 pHash 兜底存在的理由。

   `tools/mock-review/verify.js` 是一个**独立写出来的参考客户端**：它不从服务端 import 任何东西，只按 `docs/tuping-design.md` 的协议文本实现一遍，所以同一个脚本既能对着 mock 跑，也能对着真服务端跑（`--base`）。在相信任何一端之前先跑它：

   ```powershell
   cd tools/mock-review
   npm install
   node server.js                       # 终端 1
   node verify.js                       # 终端 2：对着 mock
   node verify.js --base http://127.0.0.1:8080   # 或者对着真服务端
   ```
7. **mock 上针对时序相关行为的开关** —— 一个"下一张下载期间保持当前照片"的查看器没法靠读代码来检查，而在局域网上等待又短到看不见。`__control/slow-media?ms=12000&sizes=o` 让原图晚十二秒到达，`__control/delete-photo?id=N` 像主持人整理聚会相册那样删掉一张照片。两者都不改变协议长什么样 —— 只改变它花多久，以及下一次读库时里面有什么。

   翻页队列和删除路径就是这样在模拟器上确认的：原图变慢时，连排 7 次翻页会让屏幕上那张照片保留，角上出现五个箭头和一个 `+2` 溢出，指针停下的那张到达时顶替它 —— 这两种情况下黑帧都会暴露出来。（当时每一次按键都会排进队列、依次显示；现在只取指针停下的那一张，见第 11 条。）向正在运行的幻灯片上传照片，把信息条里的计数从 `4 / 16` 变成 `4 / 17`；删掉同一张照片后，两次轮询之后又变回 `4 / 16`。

   慢速媒体开关还发现了队列第一版里的一个真实 bug：可见那张照片**后面**的那张，往往正是队列在等的那张 —— 往回翻就是显然的例子 —— 而那一层已经把它加载完成了，所以永远不会触发任何加载回调，箭头就永远停在那里。现在各层既追踪自己实际显示的是什么，也追踪自己被要求加载的是什么。
8. **主题和配乐，在真机上** —— 两者都无法从代码里读出来。主题从 **设置 → 主题** 切换后逐屏走了一遍：设置页、时间线和一个月份网格在浅色下，以及重启之后的同一个应用 —— 它回到浅色，因为窗口在 Compose 绘制之前就被填上了浅色背景；把同一行切回深色，样子不变。查看器在两种模式下都保持深色 —— 它是覆在照片之上的一个面，不是覆在应用之上。音乐则按遥控器的走法走了一遍：列表在该行上方展开、勾选、同一次按键把它取消、两首都勾上、列表关闭且焦点仍在唤出它的控件上、该行关闭且没有启动任何东西、左右键在列表底下完全不起作用 —— 那一次按键后画面与前一帧逐字节相同 —— 以及重启之后那两个勾仍在。

   音频本身是从设备上读出来的，而不是推断的。幻灯片运行时 `dumpsys audio` 列出 `pack: com.tvphoto.debug` 通过 `media3` 的 `AudioFocusManager` 持有 `USAGE_MEDIA / CONTENT_TYPE_MUSIC` 焦点，且 `AudioOut_D` 线程已退出待机；停止幻灯片之后，以及中途离开查看器之后，该焦点条目消失，线程回到待机。仅有焦点**不能**区分播放与暂停 —— 暂停的播放器停在 `STATE_READY` 时 `media3` 仍持有它 —— 所以暂停路径是从输出线程读的：设置行展开时该线程掉到 `0 active` 轨道并待机，该行关闭时回到一条活动轨道。把幻灯片停在视频上做同样的测量，也读到 `0 active`，而这是那里唯一可能是音乐的轨道数 —— mock 的视频不带自己的音轨（`soun` 和 `mp4a` box 不存在），所以它上面若有活动轨道只可能是音乐。唯一没有在设备上等完的是两首四分钟曲目的完整一轮：勾选的曲目按列表顺序播放并循环，这一点由 `SlideshowMusicTest`（无论勾选顺序如何，选择都按目录顺序存储）和播放器在该播放列表上的 `REPEAT_MODE_ALL` 钉住。
9. **三条只有在慢速或混合媒体库上才会显形的查看器规则** —— `__control/slow-media?ms=30000&sizes=o` 加上清空图片缓存让一张照片要花半分钟，这是看到其中任何一条的唯一办法。黑窗口在那期间是加载指示器，照片接替它时不留残余。同样延迟加上幻灯片运行时，幻灯片的下一张在飞的时候角上是**空的**，而按下按键的一瞬间就出现一个箭头 —— 一次按键，一个箭头，来自一个两者都装着的队列。而在设为顺序时，走过一个视频位于 `4 / 16` 的月份读出的是 `1 → 2 → 3 → 5 → 6 …`：视频被跨过，位置轨迹一次也没有出现 `VID_`。幻灯片运行时手动停到那段视频上也不会让它卡住 —— 它得到一个间隔，幻灯片就走到下一张。`SlideshowOrderTest` 在设备之外、对随机抽取的每个种子钉住同样的规则。
10. **翻页指针、预取窗口和曲目目录** —— 三项只存在于屏幕上的改动。`__control/slow-media?ms=12000&sizes=o` 加上清空图片缓存，把指针走动放到截图能抓到的位置：按一次右是一个右箭头，接着按一次左把那一步退掉、角上**空**了，只有再下一次按键才出现一个左箭头 —— 旧的队列把那第二次按键读成了两个向左的箭头。两个方向反复做，箭头会像指针那样递减并抵消。预取新的"让位"是量出来的而不是看出来的，办法是读 mock 的请求日志：冷缓存下查看器打开后的两秒里，它发出了**一个**原图 —— 就是屏幕上那张 —— 而同一份构建在 `hold = { false }` 时发出了**五个**，可见那张重复两次外加三次预取（`/__control/media`）。十四秒后照片落地，窗口已自行恢复（五个原图）。（这条量的是**网格与手动翻页**下的让位；查看器里让位改成"收窄到一路"、放映时窗口覆盖整份列表，是后来在一台真实 NAS 上定的，见第 15 条。）曲目列表在装着九首的情况下走了一遍：它在勾选那行打开、自己滚动到最后一行、勾上它并取消原先自带的那两首。最后这个状态 —— 恰好勾选一首，且是新七首之一 —— 随后被播放，并像第 8 条读音频那样从设备读出：`media.audio_flinger` 对 `com.tvphoto.debug` 报告 `1 Tracks of which 1 are active`、`Standby: no`，日志里带着 `ExoPlayerImpl` 的初始化和为它构建的音频 `MediaCodec`，没有任何关于资源缺失的信息。`SlideshowMusicTest` 是在设备之外让目录保持诚实的东西：目录里每个名字都必须真的在 APK 里，而且**反过来也成立** —— `assets/music` 里只要有一个文件不在目录中，构建就失败。后者是 1.3.7 把目录从九首减到四首时补上的：删条目容易，删文件容易忘，而没人能选的那 35 MB 会跟着每一次下载走。

11. **图标** —— 没有测试能证明一张图看起来对，所以新图标是渲染出来看过之后才落到矢量里的：先在 512 / 192 / 96 / 48 四个尺寸下渲染，再套上圆形和圆角方形遮罩，模拟自适应图标在桌面上被裁切的样子。构建之后用 `aapt2 dump badging` 确认 `application-icon` 指向 `res/mipmap-anydpi-v26/ic_launcher.xml`，且 APK 里同时带着 API 23–25 的回退项；系统自己画出来的那个图标是在 TV 模拟器的 **设置 → 所有应用** 里看的。

12. **预览原图、翻页只取一张、视频的 TLS 信任，在模拟器上对着 mock 走了一遍** —— 三项都只有在设备上才看得出来。设置页里新增的 预览原图 行走了一遍：默认 仅用于幻灯片播放，按 OK 依次变成 是 → 否 → 回到默认，选择写进偏好；它真的决定取哪一档也是量出来的 —— 读 mock 的请求日志（`/__control/media`），默认下查看器和它的预取窗口只发 `/m/`（1920px 大缩略图），一条 `/o/` 都没有。翻页在冷缓存下重走了一遍：清掉图片缓存、重启应用、打开当月那一项（mock 把一段视频放在该月第一项；此时前端图层正在取图，预取窗口收窄到一路，所以请求日志里几乎只有它自己的流量），连按三次右键后信息栏读数是 `4 / 15` —— 指针走三格、只取第三格那张，中间两张既没有上屏、也没有为它们发出过请求；旧的队列会先把它们取回来依次显示。视频是在 **HTTPS + 自签名证书** 的 mock 上打开的：mock 日志记到 `/p/api/v1/stream/v/1000`，`logcat` 里是 `ExoPlayerImpl Init` 与 `c2.goldfish.h264.decoder` 在解码，屏幕上是视频画面 —— 这条路径以前会以 `Trust anchor for certification path not found` 失败。清除图片缓存那一行也被走到并按了下去，显示 缓存已清除：它过去被切在屏幕外，只剩一个没有文字的圆角框。翻页规则、预览档位和 `stillUrl` 的回退都离开了设备：`PagingQueueTest`（9 条）、`PreviewOriginalTest`（4 条）和 `StillUrlTest`（8 条）在 `testDebugUnitTest` 里钉住它们。

13. **「原图」按钮，逐帧看了一遍** —— 这一条只有屏幕能证明：它涉及「加载期间屏幕上是什么」。把 mock 的原图延迟到 5 秒（`__control/slow-media?ms=5000&sizes=o`），然后：按 ↑ 打开信息条，详情里写着 **缩略图**，D-pad 已经落在 **幻灯片左边的 原图 按钮** 上；按 OK 之后，请求日志里只多出**一条** `/o/`（预取窗口同步收窄到一路，所以没有别的流量），按钮随之呼吸 —— 两张相隔一秒的截图显示它在变暗变亮，而照片**始终在屏幕上**，没有黑帧；五秒后原图到手，同一张照片原地换上去（位置仍是 `1 / 15`），**原图 按钮消失**、详情角标变成 **原图**、D-pad 回到 幻灯片。随后翻到第 2 张，角标回到 缩略图、按钮重新出现；走到那段视频上则既没有角标也没有 原图 按钮 —— 它的原图就是正在播的那条流。`StillUrlTest` 在设备之外钉住这条规则的两个前提：同一个 URL 同时是两档时（服务端只给了一个地址）算原图、且不提供按钮；视频永远没有「原图静帧」可换。**左右键的归属**也在这台机器上定过：`1 / 15` 上按 ←，高亮跳到 幻灯片 而**照片原地不动**，再按 → 回到 原图（两个按钮都在时，左右键属于这一行）；角上只剩 幻灯片 时（视频停在 `3 / 15`）按 → 仍然翻页，落到 `4 / 15`。

14. **检测升级：三条路径都在模拟器上按用户真正的走法走了一遍** —— 这一行只有屏幕能证明。**对着真实 GitHub**：进设置页自动查一次，那一行从 检查中… 变成 **已是最新版本**（此时最新 release 上还没有 `version.json`，所以走的正是 tag 重定向那条兜底 —— 一条先吃 404、仍然给出正确答案的路径），按 OK 手动重查同样如此；把仓库名临时指向一个不存在的仓库，屏幕上才是 **检查失败** 加 按 OK 重试。**下载、校验与安装**要先有一份带 SHA-256 的清单才能走，所以那一段是喂给它的：一个本地 HTTP 服务按 `version.json` 的格式发清单和 APK（限速到约 4 MB/s，好让进度那一帧截得下来），应用的地址常量临时指向它 —— 跑完已改回，没有提交。于是走了一遍：**有新版本 1.3.2** 连手动兜底那句都在 → 按 OK 先撞上 **需要允许安装**（系统里这项授权当时是关的，所以它没有白下 73 MB）→ 按 OK 打开系统的 安装未知应用 面板、打开开关 → 回来再按 OK → **正在下载 50%** → 下载完成后**系统安装器自己弹出来**问「要更新此应用吗？」（`dumpsys` 里前台是 `com.android.packageinstaller`），校验通过的文件落在 `Android/data/…/files/updates/FN-tvphoto-1.3.2.apk`，字节数与清单里的 `sizeBytes` 一致 → 取消安装器后再按 OK，安装器**重新打开而文件时间戳没变**，可见没有重新下载 → 最后把清单里的 SHA-256 改成一个错的值、删掉本机文件、重启应用让它重新取一次清单（否则它校验的是已经取到的那份旧清单，我第一次就是这么把自己骗过去的），再按 OK：日志里是 `update download did not match the manifest hash`，那一行变成 **安装包校验失败**，而那个不匹配的文件**不在磁盘上**（`updates/` 为空）。这一条是按「文件必须消失」验的，不是按屏幕上的字 —— 它正是这套东西存在的理由。离开设备的那一半由两个套件钉住：`AppVersionTest`（13 条 —— tag 的前导 `v`、缺的段、预发布后缀、读不懂的字符串，以及「名字或版本代码任一更新就算有新版本」）和 `UpdateCheckerTest`（11 条 —— 清单缺字段、哈希大小写与空格、错误页当成清单、还没有 release 时不能把路径里的数字当版本，以及「两个来源答案不同时给更新的那个」）。另外，v1.3.3 真的发布出去之后，模拟器上那台装着 1.3.1 的应用进设置页时自己把那一行变成了 **有新版本 1.3.3** —— 报告这条路是对着一份**真实发布出去**的 release 验的，不只是对着 mock 验的。

15. **签名校验，以及一台真电视在它里面找到的 bug** —— 这道校验的用意是拒收「不是本应用密钥签的 APK」，也正是它让清单可以来自镜像。它在 1.3.5 发出去，然后在作者自己的电视上**拒收了一次真实的更新**，屏幕上写的是 **安装包签名不对**。根因是一个平台不对称：`getPackageArchiveInfo` **只在传了旧标志 `GET_SIGNATURES` 时才会去解析 APK 的证书**，所以只要新标志时它照样返回一个 `PackageInfo`，但里面的签名信息从未被填过 —— 而**已安装的应用**走的是系统数据库，两种标志都答得出来。于是「空」被读成了「是别人签的」。改了三处：两个标志一起传；新字段为空时回退到旧字段；**「读不出来」不再等于「不一样」** —— 只有确实读到且确实不同才拒绝，因为挡掉一次正当更新，比它所防的那个风险更糟，而安装器本来就会执行同一条规则。验证方式是在模拟器上给一个 debug 签名的构建喂一份「描述 debug 签名的 APK」的清单：判定为一致、安装器打开，而且日志里**没有**那句「读不出证书」—— 两种情况在屏幕上长得一模一样，全靠这行日志区分。离开设备的那一半由两个套件钉住：`AppVersionTest`（13 条）和 `UpdateCheckerTest`（11 条 —— 其中一条专门钉住「两个来源答案不同时，给的是更新的那个，而不是先到的那个」）。

16. **四条只有在真机上才看得出的东西，对着一台真实 NAS 走了一遍** —— 服务器是公网穿透地址，相册是「他人分享」里那份 217 张的（原图 4–12 MB，链路上单张要十几秒），不是 mock。**① 图评连不上**：服务端起着，地址从模拟器内部也连得通（`toybox nc`），按钮却是灰的 —— 电视里存的地址尾部多了一个 **NUL**，`trim()` 去不掉它（NUL 不是空白），`HttpUrl` 于是拒绝解析，整层关闭，而日志说的是「地址为空或不是 URL」。改成**读写两头都清洗**（并复用 NAS 地址行早就有的全角折叠）之后，坏值在读取时自己就好了：日志变成 `answered and accepts this device`，服务端签发设备令牌，库里 49 张照片 / 49 个短码、`base_url` 正是电视上报的那个公网地址，二维码在屏上。**② 幻灯片里的原图**：8 秒间隔下屏上是缩略图、30 秒下是原图，而原图一直在往磁盘缓存里落 —— 到点被取消的正是**它自己**的下载。改完之后（忍耐上限跟随间隔、到点保留在途下载并原地换层、窗口收窄而不是停掉、放映时覆盖整份列表），同一场 8 秒随机放映连续约 20 张**全是原图**；内存 Native 50→62 MB 到顶回落、PSS 137→169 MB、4 分钟以上无崩溃（改前约 7 分钟 `OutOfMemoryError` 落在 OkHttp reader 线程上被杀）。**③ 弹幕行数**：`少` 最多 2 行、`多` 最多 4 行，按行轮流、一行里后一条要等前一条尾部让开 200px（≈0.9 秒）；高度按**整屏**算（2 行 ≤ 1/4、4 行 ≤ 2/5），实测文字 y 在 少 是 118 / 205（末行文字底 247.5 ≤ 270）、多 是 113 / 197 / 281 / 365（底 415 ≤ 432）。**④ 评论长度**：从 80 字收到 **20 字**（一行最多占屏宽 45% = 864px，字号 34 / 40 下一行约 25 / 21 个汉字，所以 80 字里有五六十个字只能变成省略号）：21 字被 400 `too_long` 拒绝、20 字通过。四条都在设备上验过，离开设备的那一半由 `ReviewAddressTest`（10 条）、`DanmakuFeedTest`（20 条）、`StayExtensionTest`（8 条）和服务端 `go test ./...` 钉住；根因与取舍写在 [`tuping-design.md`](tuping-design.md) 的 §17.12–17.14。

17. **幻灯片走不出第一页** —— 现场是「播放五六十张之后，又从第一张开始播放。后边其实还有很多照片」，而**"五六十"就是答案**：`PAGE_SIZE = 60`，网格一次取一页，那个相册是 217 张照片 + 6 个视频 = **223 项**，而**查看器从不请求下一页** —— `loadMore()` 全项目只有一个调用点，是网格的滚动检测。于是放映在那 60 张里循环，第 61 项起从没被请求过（"后面的缩略图还没加载出来"是同一个根因的第二个症状，看上去像另一个 bug）。改成共用的纯规则 `needsNextPage`（末尾前 8 行；**放映中无条件**，因为随机放映的下一张来自列表任意位置）之后，模拟器上实测：手动翻页第 50 次读数 `51 / 60`（还没到触发线 52），第 65 次变成 **`66 / 120`**（列表自己长大、指针越过 60 而不回头）；按下「幻灯片」**3 秒**后读数从 `120` 变成 **`223`**（相册全部项目），19 秒后已在 **`192 / 223`**（随机顺序）。`NextPageTest` 5 条钉住那条规则；根因写在 [`tuping-design.md`](tuping-design.md) 的 §17.16。

18. **手机上删掉的评论从电视上消失，以及缓存里的原图被直接画出来** —— 两件事都只有屏幕能证明，都在模拟器上对着 mock NAS、图评指向本机服务端走了一遍。在 H5 管理员页删掉 `ZZ-DELETE-ME-1`（303 `?ok=deleted`）之后，它飘完当前这一趟就再没出现过：每 2 秒 dump 一次无障碍树，第 4、8 秒还在，**第 12 秒起一分钟内再也没有**；随后新发一条 `ZZ-CONTROL-2` **2 秒内**出现，说明 socket 在删除之后仍然好好的。不靠服务端的那一半是 `mergeCommentStates`（7 条）——按 id **覆盖**而不是只追加。原图那一半：冷缓存时读数 `缩略图` 加「原图」按钮，按下去原图进缓存，翻到下一张（从没取过原图）仍是 `缩略图`，**翻回上一张直接是 `原图`**，没人按过任何东西；退出查看器再打开同一张也一样。把 预览原图 设成 **否**，同一张（原图就在缓存里）仍是 `缩略图` + 「原图」按钮 —— 那正是这个选项的意思。`PreviewOriginalTest` 6 条钉住这条规则；两件事分别写在 §17.17 与 §17.18。

19. **换了一台服务器之后，屏幕上那张码会自己换掉** —— 报告来自真机（"我构建了新的 server 端，扫码后提示这张照片不在图片数据库里"，H5 页的原话是 **这张照片不在图评里**），而根因是用**那台服务器自己的回答**定位的：它的 `/healthz` 是 `uptimeSec:331` / `thumbBytes:0`（缩略图目录空的）；电视日志在 11:52:46 —— 与新服务器起来的时刻同一分钟 —— 写着 `does not accept this device's token; registering again` 紧跟 `live socket closed: … '404 Not Found'`；而电视缓存里那两个短码对着新服务器取回来都是 **404**。也就是说它重新注册了**设备**，一张照片都没重新注册，因为 1.4.2 那道修复按设计保留了照片侧的身份，理由是"重新注册后同一张照片会回到同一个身份"—— 这句话只在服务器**还持有那些行**的时候成立，而那道修复存在的理由恰恰是它不持有。修完之后在 **Android TV 模拟器**上对着 `tools/mock-review` 走完了整个换服务器过程：对着 mock 注册出一张码（`vloRGE`，`GET /c/vloRGE` → **200**）→ **杀掉 mock、换成一个空的重启**（`uptimeSec:5`、`thumbBytes:0`，`vloRGE` → **404**，报告的现场复现）→ 回到网格再打开同一张照片，日志依次是 `does not accept this device's token; registering again` → `issued a new device; forgetting its old answers` → `registering 1002 again; its code came from the old server`，磁盘上那张旧码被删掉、换成了新码（`WEAC5P` → 新 mock 上 **200**，`vloRGE` 仍是 404）。同一轮里"历史读回 `not_found`"那条自愈也自己触发了（`the server does not hold 006GJPZ9…; registering it again`）。离开设备的那一半是 `ReviewRecoveryTest` 6 条：一次修复**只报告一次**"服务器被换掉了"、掉包不算拒绝、领不到设备的拒绝不算换服务器、两个调用同时被拒只领一个设备、`not_found` 是"服务器没有这张照片"、其余协议回答都不是。根因、取舍与一处刻意的顺序（只有屏幕上有码时才重注册）写在 [`tuping-design.md`](tuping-design.md) 的 §17.24。

20. **发评论端点自己的额度：120 条/分** —— 服务端单测 `TestCommentBudgetIsWholeService`。§7 原本三档按调用方算的额度都能靠换 cookie／换 IP／换图片绕开，所以端点本身要有一道不看来源的上限。测试是唯一能看见它的形状：五个回环源地址（各 30 条/分的 IP 额度）加每条请求换一个 `anonId`（各 5 条/分），谁都没有超自己的线，端点仍然在第 121 条上拒绝。变异检查做过 —— 把 handler 里那一行注释掉，同一份测试报 `the endpoint took 122 comments, want exactly 120` 并失败。**发出去的二进制也量过，不只是源码**：`server-v0.1.2` 那个 release 里的 `tupingd-linux-amd64` 在 WSL 里跑起来（`-version` → `0.1.2`，监听日志也是 `version=0.1.2`），再从 WSL **内部**用五个回环源地址发 122 条评论 —— 窗口里恰好 **120 条 200、2 条 429**，被拒的那条读作 `{"error":{"code":"rate_limited","message":"发得太快了，歇一会儿"}}`。这一步一开始是在 Windows 上做的，结果只到 36 条：Windows 到 WSL 的 localhost 转发会把连接重开成 127.0.0.1，五个源地址变成一个，先撞上的是每 IP 30 条/分 —— 测量工具本身把被测对象挡住了，这才是"从 WSL 内部发"的原因。取舍写在 §17.25。

21. **登录状态过期后的 401 重试** —— 报告是"app 打开后长时间放着不动，页面上会显示 401，有个重试按钮，点了没用，退出登录重新登录才能正常工作"。
    重试这条路修成"和重新登录完全一样"：`SessionRecovery` 决定什么时候该重登（只有 `code 401/5001`，网络超时和证书问题不重登）、什么时候不该绕圈（一次调用只重登一次），`SessionRepository.reSignIn` 先关掉旧的登录 socket 再跑完整握手（访问码网关也重跑一遍）——也就是退出登录再登录所做的同一件事。9 条 `SessionRecoveryTest` 在设备之外钉住这些规则。
    **设备上对着 `tools/mock-nas` 走了一遍**（模拟器，应用指向 `10.0.2.2:5667`，重启 mock 让它手里的 token 集合清空，于是应用手里那个 token 作废）：
    - 进入另一个分区触发重新读列表，屏幕上出现「加载中…」，**3 秒后列表自己回来了**（6 项相册，1155 张照片的合计仍在），期间没有登录表单、也不需要按任何键。mock 日志里是第二次 `[ws] login ok`。按 重试 这条路因此不再需要有它自己的行为 —— 分区自己的重新核对走的就是同一套。
    - 这一遍还抓到了修复里真正的 bug，而它不是靠读代码看出来的：第一版把"刷新有没有发生"实现成**比较两个 token**，相等就当作"什么都没刷新"，于是把原始 401 直接抛出去。mock 的 token 形状是 `mock-token-<user>`，第二次登录发回来的是**同一个字符串** —— 屏幕上于是又出现 `出错了 · access token expired (code 401/5001)` 加重试按钮，和报告里一模一样。日志里 `refreshing; stale token=mock-token-v` 紧跟 `refreshed; new token=mock-token-v` 把它钉死了。token 是不透明字符串，两个相等可以属于两个不同会话，所以判据换成 `sessionGeneration`（每接受一次握手会话加一），比较 token 那版作为一条测试保留在 `SessionRecoveryTest` 里。
    - 登录**失败**那一半（访问码被改掉、NAS 不可达）的行为没有在设备上走：`reSignIn` 失败会把 `SessionState.Failed` 发出来，界面于是回落到登录表单并把服务器给的原因写在上面，这一点由 `withSession`/`refreshSession` 的代码路径和 9 条单测覆盖。

22. **设置页改成两栏** —— 报告是"设置页面太长，太乱了"，要求左分类右分页。在模拟器上对着 mock 走了一遍：分类是 **版本升级 / 通用 / 幻灯片设置 / 图评设置**，四个分页各自的标题、说明和内容都截了图；焦点留在左侧分类上，右键进入右侧，**上下移动分类时右键不抢焦点**。
    这里有两处是走出来才发现、读代码看不出来的：
    - **行里右侧的值被挤成一列竖排汉字**。原来标签列固定 360dp，值只剩行内剩下的宽度，1080p 下 `已是最新版本` 于是**一个字一行**地贴着右边缘排下来，行也高得离谱 —— 看上去像渲染坏了。改成 1:1 权重之后另一个问题冒出来：长提示文字与值**叠在一起**（截图里「幻灯片播放时也一样…」压着「仅用于幻灯片播放」）。最终是权重列 + `TextAlign.End` + `maxLines` + `TextOverflow.Ellipsis` 一起用。
    - **请求焦点会把分页标题滚出屏幕**。切到某个分页时给它第一行请求焦点，`requestFocus` 会把它滚进视野 —— 而分页是每次重新组合的，于是标题和说明被顶出屏幕，用户看到的是一列没有标题的行；更糟的是滚动位置由同一个列保留，**下一个分页也继承它**。现在焦点停在左侧分类上，右侧用右键进入；「第一行」的焦点请求去掉了。`focusRestorer()` 留在根 `Row` 上，从照片退出回来时光标回到离开的那一项。
    正文字号、右对齐、以及 240dp 的分类列在浅色主题下也各看了一眼。

还有一个是靠报告症状、而不是读代码发现的：

- **退出登录、再登录 → `errno 401`。** 请求 id 内嵌了登录返回的 session id，但这个生成器是进程级单例，活得比退出登录更久，于是第二次握手对外宣告的是**上一个**会话的 id。mock 服务器此前默默接受了这一点，因为它完全忽略 `reqid` —— mock 的严格程度只等于它检查的字段。现在它会强制 session id 的新鲜度，`verify.js` 断言这次拒绝，所以去掉 `FnReqId.reset()` 会让流程大声失败，而不是悄悄回归。登录错误现在也带上服务器自己的措辞，因为光一个 `errno 401` 无法行动。
